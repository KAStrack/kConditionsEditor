# kConditionsEditor

A zero-dependency JavaScript conditions builder that takes over a `<textarea>`, plus
evaluator SDKs that turn the JSON it writes into a boolean anywhere else in your stack.

[Live demo and documentation →](https://kastrack.github.io/kConditionsEditor/)

```
If ([Name] matches regex "^ben" AND ([Date of Birth] is before "1980"
    OR ([Date of Birth] is before "1982" AND [State] is one of ["Florida", "Texas"])))
```

That rule is built by clicking, stored as JSON, and evaluated identically in the browser
and on the server.

---

## Why

Rule builders usually stop at the browser: you get a nice UI and a bespoke blob that only
one codebase knows how to read. kConditionsEditor separates the two halves.

- **The editor** is a plain script. No build step, no framework, ~30 KB of JavaScript and
  a stylesheet you can retheme with CSS variables. It hides your textarea, renders a
  nested builder in its place, and rewrites the textarea's value on every change — so
  your form keeps posting exactly as it did before.
- **The document** is small, versioned, self-describing JSON with a published
  [specification](SPEC.md) and [JSON Schema](schema/condition-document.schema.json).
- **The SDKs** take that document plus a flat set of field values and return `true` or
  `false`. JavaScript/Node and PHP ship today; both run the same conformance fixtures, so
  they cannot drift apart.

## Install

### Browser

One CSS file and one JS file, from `dist/`:

```html
<link rel="stylesheet" href="dist/k-conditions.min.css">

<textarea id="conditions" name="conditions"></textarea>

<script src="dist/k-conditions.min.js"></script>
```

That bundle is the editor, the evaluator and the SQL builder together, with every
skin — 21 KB over the wire, gzipped. It sets both `KConditions` and
`KConditionsEditor` on the global.

Or load the sources directly, which is the same thing unminified and is what the
demo pages do:

```html
<link rel="stylesheet" href="src/k-conditions-editor.css">
<link rel="stylesheet" href="src/k-conditions-skins.css">

<textarea id="conditions" name="conditions"></textarea>

<script src="src/k-conditions-evaluator.js"></script>
<script src="src/k-conditions-editor.js"></script>
```

The evaluator must load first — the editor uses its operator metadata. The skins
stylesheet is required for every skin except `boxed`, and
`src/k-conditions-sql.js` only if you want SQL output.

### What is in `dist/`

| File | What it is |
|---|---|
| `k-conditions.min.css` | base + every skin, minified — the one stylesheet |
| `k-conditions.min.js` | evaluator + SQL + editor, minified — the one script |
| `k-conditions.css` / `.js` | the same two bundles, unminified, for debugging |
| `k-conditions-*.min.css` / `.min.js` | one minified file per source, if you want to pick |

`dist/` is generated by `npm run build`. The published npm package carries it
(`prepublishOnly` runs the build), so installing from npm never requires a build
step — but a git clone starts without it, so run the build once after cloning.
The sources stay the deliverable: edit `src/`, then rebuild.

The build also copies the minified files into `docs/dist/`, which the GitHub
Pages site in `docs/` loads. That copy is committed, because Pages serves the
repository as it stands.

### npm

```bash
npm install @kastrack/conditions-editor
```

### Composer

```bash
composer require kastrack/conditions-editor
```

Not using Composer? `require __DIR__ . '/kConditionsEditor/sdk/php/autoload.php';`

## Quick start

```js
const editor = KConditionsEditor.attach('#conditions', {
  emptyText: 'Always',
  fields: [
    { name: 'name',  label: 'Name',          type: 'text' },
    { name: 'email', label: 'Email',         type: 'text',
      comparableWith: ['billing_email'] },
    { name: 'billing_email', label: 'Billing Email', type: 'text' },
    { name: 'dob',   label: 'Date of Birth', type: 'date' },
    { name: 'state', label: 'State',         type: 'enum',
      choices: ['Florida', 'Louisiana', 'Texas', 'Mississippi', 'California'] }
  ],
  onChange(document, { valid, problems }) {
    submitButton.disabled = !valid;
  }
});
```

The user sees a collapsed summary — "Always" until they build something — and an **Edit
Conditions** button. Opening it reveals the nested builder.

Then on the server:

```php
use function Kastrack\ConditionsEditor\evaluate;

if (evaluate($_POST['conditions'], $submission, ['environment' => 'server'])) {
    // do the thing
}
```

Or in Node:

```js
const K = require('@kastrack/conditions-editor');

if (K.evaluate(document, submission, { environment: 'server' })) {
    // do the thing
}
```

## What the editor produces

```json
{
  "version": "1.0",
  "generator": "kConditionsEditor/0.1.1",
  "operators": {},
  "root": {
    "type": "group",
    "operator": "and",
    "negate": false,
    "children": [
      {
        "type": "condition",
        "field": "name",
        "operator": "regex",
        "values": [{ "source": "literal", "value": "^ben" }]
      },
      {
        "type": "group",
        "operator": "or",
        "children": [
          {
            "type": "condition",
            "field": "dob",
            "operator": "date_before",
            "values": [{ "source": "literal", "value": "1980" }]
          }
        ]
      }
    ]
  }
}
```

A value is either a literal or a pointer at another field
(`{ "source": "field", "field": "billing_email" }`). An empty `children` array means "no
conditions", which evaluates to `true` — the "Always" case.

## Operators

Thirty-two builtin operators across seven groups — equality, arithmetic, alphanumeric,
list, date, boolean and existence. Each field advertises which it accepts, either by naming them or by
pulling in whole groups:

```js
{ name: 'dob', type: 'date', operators: ['group:date', 'is_set'] }
```

With no `operators` list, the field's `type` picks a sensible default set.

The full table, with the comparison and date-parsing rules, is in [SPEC.md](SPEC.md).

### Field choices

A field's `choices` — and a custom `values` operator's `values` — may be written three
ways. All three mean the same thing: the first item is what gets stored in the document,
the second is what the user sees.

```js
choices: ['Florida', 'Texas']
choices: [{ value: 'FL', label: 'Florida' }, { value: 'TX', label: 'Texas' }]
choices: { FL: 'Florida', TX: 'Texas' }        // an associative map
```

Labels are used everywhere the rule is shown — the dropdowns, the collapsed summary, and
`describe()` — so a rule reads `[State] is equal to "Florida"` while the document stores
`"FL"`.

**Except where the operand is not a choice.** `contains`, `does not contain`, `starts
with`, `ends with`, `matches regex` and `does not match regex` take a *fragment or a
pattern*, not one of the values, so on those the editor shows a free text box rather than
the dropdown, and `describe()` prints what was typed:

```
[State] is equal to "Florida"     ← eq: a whole value, so the label
[State] contains "FL"             ← contains: a substring, left alone
```

Operators carry this as `valueFromChoices` in their metadata; a custom operator can set it
`false` to get the same treatment.

### Custom operators

Two kinds, both declared at initialisation and copied into the document when used, so the
JSON stays portable.

**A fixed set of values:**

```js
is_gulf_state: {
  kind: 'values',
  label: 'is a Gulf state',
  match: 'in',
  arity: 0,
  values: ['Florida', 'Louisiana', 'Texas', 'Mississippi'],
  appliesTo: ['state']
}
```

**A host function:**

```js
email_is_unique: {
  kind: 'callback',
  label: 'is not already registered',
  arity: 0,
  availableIn: ['server'],
  callbacks: {
    php:    { class: '\\App\\Rules\\Email', method: 'isUnique', static: true },
    js:     { function: 'emailIsUnique' },
    python: { module: 'app.rules', function: 'email_is_unique' }
  },
  policy: {
    unresolved: { client: 'skip', server: 'error', '*': 'error' }
  }
}
```

Each SDK resolves the binding for its own runtime. **Dispatching on a name taken from a
JSON document is arbitrary code execution**, so every SDK checks its own registry first
and ignores the `callbacks` block unless you explicitly pass
`allowManifestCallbacks: true`. Registering the callable yourself is the recommended
route:

```php
$evaluator->registerOperator('email_is_unique', fn ($value) => !User::emailExists($value));
```

## Conditions that only work in one place

"Is this email already registered?" can only be answered on the server — but you would
still like to pre-check the rest of the rule in the browser before letting someone submit.

Give the operator a policy keyed by context:

```json
"policy": { "unresolved": { "client": "skip", "server": "error", "*": "error" } }
```

Then construct each evaluator with the context it is actually running in:

```js
new KConditions.Evaluator({ environment: 'client' })   // in the browser
new KConditions.Evaluator({ environment: 'server' })   // under Node, server-side
```

Labels are matched in order: each entry of `profiles`, then `environment`, then `runtime`
(`js`, `php`, …), then `"*"`. So you can key a policy by deployment tier, by language, or
by any custom label you invent — and the same rule file behaves correctly in both places.

Policies resolve to one of four outcomes:

| Policy  | Effect                                                       |
|---------|--------------------------------------------------------------|
| `skip`  | The condition behaves as if it were not in the document       |
| `true`  | The condition evaluates to `true`                             |
| `false` | The condition evaluates to `false`                            |
| `error` | Evaluation aborts and the SDK raises                          |

The default when the document says nothing is `error`, changeable per evaluator with the
`unresolvedPolicy` and `errorPolicy` options.

### What skipping means, precisely

A skipped condition behaves as though it were **never in the document**. It is dropped
from its parent's children and the siblings decide the group. If every child of a group is
skipped, that group is skipped too and drops out of *its* parent, and so on. If the whole
document ends up skipped, the evaluator returns its `emptyResult` (default `true`).

This holds for `and` and `or` alike — a skipped condition can never turn an `or` true on
its own. Everything skipped is listed in the detailed result, so a server-side pass can
see exactly what the client deferred:

```js
const details = evaluator.evaluateDetailed(document, data);
details.result;   // boolean
details.skipped;  // [{ path, field, operator, reason }]
details.errors;   // handled failures, when the policy was true/false
```

## The result hook

Every SDK entry point takes an optional trailing callable. When supplied, the SDK returns
**that callable's** return value instead of the boolean. It receives the original call's
arguments, then the computed result, then the details.

```js
const outcome = K.evaluate(document, data, options,
  (document, data, options, result, details) => {
    metrics.increment(result ? 'rule.pass' : 'rule.fail');
    return { ok: result, deferred: details.skipped.map(s => s.operator) };
  });
```

```php
$outcome = evaluate($document, $data, $options,
    function (array $document, array $data, array $options, bool $result, $details) {
        Log::info('rule evaluated', ['skipped' => $details->skipped]);

        return new RuleOutcome($result, $details->skipped);
    });
```

## Showing a rule to a reader

A stored document is JSON. To put it in front of someone — a confirmation page, an audit
log, an email — both SDKs render it as a sentence.

```js
KConditions.describe(document, { fields });
// [State] is equal to "Florida"

KConditions.describeHtml(document, { fields });
// <span class="kcd"><strong class="kcd-field">State</strong> <span class="kcd-op">is equal to</span> <span class="kcd-value">Florida</span></span>
```

The two say the same thing: the brackets and quotes that mark a field and a value in plain
text become a bold field and an underlined value in HTML.

```php
use function Kastrack\ConditionsEditor\{describe, describeHtml};

describe($document, ['fields' => $fields]);
describeHtml($document, ['fields' => $fields]);
```

Both take the same options — `fields` (for labels and choice labels), `operators` (custom
operator labels) and `emptyText` — and both walk the document with the *same* function, so
they can never disagree about bracketing, `NOT` placement or which label won. Only the leaf
formatting differs.

`describeHtml()` **always escapes**. There is no option to turn it off. A document is
client-supplied input — field labels, values and `emptyText` all come from somewhere you
do not control — so `<img src=x onerror=…>` in a value comes back as text, every time.
That is also why it is a separate function rather than a flag on `describe()`: the call
site says out loud that it is producing markup.

### The classes it emits

| Class | Wraps |
|-------|-------|
| `.kcd` | The whole rendering |
| `.kcd-field` | A field name (a `<strong>`) |
| `.kcd-op` | An operator phrase |
| `.kcd-value` | A value |
| `.kcd-list` / `.kcd-sep` | A list of values, and the commas between them |
| `.kcd-logic` (`.kcd-and` / `.kcd-or`) | A joining operator |
| `.kcd-not` | A negation |
| `.kcd-paren` | A bracket |
| `.kcd-join` | The word between the two halves of a two-value operator |

The stylesheet ships a default look for these — bold field, dashed-underlined value in the
value colour, italic operator, coloured `AND` / `OR` — and that block is deliberately **not
scoped to the editor**, so a page that renders a rule server-side with no editor on it can
load the CSS and get the same look. The colours defer to the editor's `--kce-*` tokens when
they are present and fall back to their own otherwise, so it also stays in step with a
theme when the editor *is* on the page.

If you would rather style it yourself, the markup is class-only — no inline styles.

### In the editor

`summaryHtml: true` renders the collapsed summary with `describeHtml()` instead of plain
text, so the field names and values in the header get the same treatment. The editor also
exposes both directly:

```js
editor.describe();      // string
editor.describeHtml();  // string of HTML
```

Both use the editor's own fields and operators, so you do not have to pass them again.

## SQL output

The same rule can be rendered as a SQL boolean expression — the part that goes after
`WHERE`. Load `src/k-conditions-sql.js` (or `use function Kastrack\ConditionsEditor\toSql`)
and you have SQL:

```js
KConditions.toSql(document, { dialect: 'mysql' });
// → `email` = 'a@b.c' AND `dob` < '1980-01-01'
```

**`column` is optional.** A field name is used as the column name unless you say
otherwise, so a schema whose columns already match your field names needs no mapping at
all — and a field the builder has never been told about still resolves to its own name.
Give a field a `column` only where the two differ:

```js
{ name: 'dob', label: 'Date of Birth', type: 'date', column: 'c.date_of_birth' }
```

The resolution order per field is `column` → `sql` → `name`, and `options.columns`
(a plain `{ field: column }` map) overrides all three — useful when the same document
is run against two schemas:

```js
KConditions.toSql(document, { dialect: 'mysql', columns: { dob: 'c.date_of_birth' } });
```

Entries in `fields` may also be bare strings (`fields: ['email', 'dob']`) when all you
want is the type defaults.

```php
use function Kastrack\ConditionsEditor\toSql;

$where = toSql($document, [
    'dialect' => 'mysql',
    'fields'  => $fields,
    'now'     => new DateTimeImmutable(),
]);

$rows = $db->query("SELECT * FROM contacts c JOIN addresses a ON … WHERE $where");
```

```sql
(`c`.`full_name` REGEXP '^ben'
  AND (`c`.`date_of_birth` < '1980-01-01'
       OR (`c`.`date_of_birth` < '1982-01-01' AND `a`.`state_code` IN ('FL', 'TX'))))
```

Dialects: `mysql` (and `mariadb`), `postgres`, `sqlite`, `sqlserver`, `standard`. They
differ in identifier quoting, string escaping, boolean literals and regular expressions.

| Option | Default | Notes |
|--------|---------|-------|
| `dialect` | `"standard"` | Which SQL to emit |
| `fields` | `null` | Supplies `column` and `type` per field |
| `columns` | `null` | Or map field name → column directly |
| `parameters` | `false` | Emit placeholders and return the values in `params` |
| `placeholderStyle` | per dialect | `question`, `numbered` or `named` |
| `quoteIdentifiers` | `true` | Turn off if your columns are already qualified |
| `nullSafeNegation` | `true` | Wrap negative operators as `(col IS NULL OR …)` |
| `now` | `null` | Resolves the relative date operators |
| `pretty` | `false` | Indent nested groups |
| `unsupportedPolicy` | `"error"` | What to do when a dialect can't express an operator |

### Where to generate it

Both places are supported, and which one is right depends on what your endpoint already
accepts.

**Server-side, from the document** — the default posture. The browser posts the JSON, the
server builds the SQL with `toSql()`. Use this when your endpoint receives a *rule* and you
would rather not widen it into accepting SQL. Nothing the client sends reaches the query
except through the document, which is a closed grammar the builder validates as it walks.

**Client-side, into the textarea** — `output: 'sql'`. Use this when the field already
accepts SQL. If a human could previously type `status = 'x' OR 1=1` into that box, then
kConditionsEditor typing a nicer expression into it adds no attack surface whatsoever: the
trust boundary is where it always was, and whatever sanitising, sandboxing and privilege
limiting you do on the way in still applies unchanged. This is the "give the non-SQL users
a friendly builder over the same field" case, and it is a perfectly sound one.

What would be wrong is the middle ground: an endpoint that today receives JSON and starts
executing client-supplied SQL because it is convenient. That is a new trust boundary, and
the answer there is to keep posting the document and build the SQL on the server.

Use `parameters: true` wherever your driver supports placeholders, in either mode.

**It is a translation, not the evaluator.** SQL has three-valued logic and the evaluator
does not, so a row-for-row match is not guaranteed. The choices made here: negative
operators are null-safe by default (`col <> 'x'` becomes `(col IS NULL OR col <> 'x')`),
`is_empty` covers `NULL` and `''`, `date_eq` becomes a half-open day range, and the
relative date operators resolve against `now` at generation time rather than emitting
`CURRENT_DATE`, so a saved query keeps the dates it was built with.

**Operators that have no SQL.** A `callback` operator cannot be translated. Give it an
`sql` template and it can be:

```js
email_is_unique: {
  kind: 'callback',
  sql: 'NOT EXISTS (SELECT 1 FROM blocked b WHERE b.email = {field})'
}
```

`{field}` is the quoted column, `{0}`/`{1}` the rendered values, `{values}` the
comma-separated list. Without a template the operator falls to the `unresolved` policy —
so `{"unresolved": {"sql": "skip"}}` drops it from the WHERE clause and evaluates it in
code instead. Regular expressions are unsupported in SQL Server and need a UDF in SQLite;
those fall to `unsupportedPolicy`.

**Writing SQL into the textarea.** `output: 'sql'` puts the expression in the textarea
instead of the JSON. It defaults to `'json'`, so you opt in.

SQL does not parse back into a rule, so the editor needs somewhere to keep the document if
the rule is to survive a reload. Two ways, depending on whether you can add a field:

*You can add a hidden field:*

```html
<textarea name="conditions"></textarea>
<input type="hidden" name="conditions_doc">
```

```js
KConditionsEditor.attach('[name=conditions]', {
  output: 'sql',
  documentInput: '[name=conditions_doc]',
  sql: { dialect: 'mysql' },
  fields
});
```

*You cannot — it is an existing SQL field and that is all there is:*

```js
KConditionsEditor.attach('#existing-sql-field', {
  output: 'sql',
  documentInComment: true,   // the rule rides along in a trailing SQL comment
  hideTextarea: false,       // let people see the SQL it writes
  sql: { dialect: 'mysql' },
  fields
});
```

which produces:

```sql
(`c`.`full_name` REGEXP '^ben' AND `a`.`state_code` IN ('FL', 'TX'))
/* kconditions:1.0 {"version":"1.0","operators":{},"root":{…}} */
```

The comment trails the expression — in a field someone can see, the SQL is the point and
the document is baggage. It is a no-op to the database, and the editor reads the rule back
out of it, so one field round-trips. Two caveats: anything that strips comments before storing the SQL
loses the rule (the SQL still works, the builder just reopens empty), and hand-edits to the
generated SQL are overwritten the next time someone touches the builder — so if you expect
people to switch between typing SQL and using the builder, keep the raw SQL somewhere the
editor does not own.

**If the field already holds something the editor cannot read** — SQL written by hand,
say, with no document beside it — the editor does not replace it. The field keeps its
content, byte for byte, until the first change to the rule, so an untouched form submits
exactly what it loaded. Meanwhile a notice above the rule shows the original text, with a
Dismiss button, so the rule can be rebuilt while reading it (labels `preservedText` and
`preservedDismiss`). `editor.preserved` is `{ text }` or `null`, `editor.pristine` says
whether the field is still untouched, and the `change` payload carries `pristine` too.
Opening the editor, changing skin or theme and re-attaching do not count as changes;
adding, editing, undoing and `setDocument()` do. There is no parser: the editor never
guesses what a hand-written expression meant.

With `hideTextarea: false` the field stays visible, which is usually what you want here:
people see the SQL being written for them, which is half the point.

## Debugging

`debug: true` adds a **View source** button to the footer, opening a tabbed panel showing
the document, the generated SQL (with its parameters, skipped operators and warnings), and
the plain-English summary with any validation problems. It is off by default because it
exposes your column names and the whole rule to anyone looking at the page.

Events: `change`, `open`, `close`, `clear`, `undo`, `redo`, `source`.

**Clear and start over** sits in the footer and asks before it acts: the button
swaps itself for an inline question, which Escape or a click elsewhere backs out
of. It hides itself when the rule is already empty. Turn it off with
`allowClear: false`, or call `editor.clear()` yourself.

### Field definitions

```js
{
  name: 'dob',
  label: 'Date of Birth',
  type: 'date',                  // text | number | date | boolean | enum | list
  column: 'c.date_of_birth',     // SQL name; defaults to `name`
  choices: [...],                // enum fields — see Field choices
  operators: ['group:date'],     // or omit for the type default
  excludeOperators: [...],
  values: ['literal', 'field'],  // which value sources are offered
  comparableWith: ['type:date'], // which fields may be compared against
  placeholder: '…',
  input: { min: 0, max: 100, step: 1 }
}
```

`comparableWith` accepts field names, `type:<type>`, `group:<group>`, `'*'` for
everything, or `false` to disable field comparison. Omit it and the field is comparable
with other fields of the same type.

### Comparing a field against another field

A value can be a literal or a pointer at another field, and where both are possible the
editor shows a small **Value / Field** selector beside the value. That selector is **off
by default** — it costs a control on every row that has a value, to buy a feature most
rules never use. Turn it on with `allowFieldValues: true`:

```js
KConditionsEditor.attach('#conditions', { fields, allowFieldValues: true });
```

Or leave it off and opt in one field at a time — naming `comparableWith` on a field is
read as asking for it, so this works with the global setting untouched:

```js
{ name: 'email', label: 'Email', comparableWith: ['billing_email'] }
```

`comparableWith: false` still wins, so a field can opt out even with the global on. And a
document that already holds a field reference always keeps its selector, whatever the
settings say — otherwise there would be no way back to a literal.

> **Changed in 0.0.21.** This used to be on by default, which meant any field with no
> `comparableWith` of its own silently became comparable with every other field of its
> type, and got the selector. If you were relying on that, set `allowFieldValues: true`.

### Building a rule

A rule grows from the logic word, not from a generic "add row" button. Every
insertion point carries a `+AND` or `+OR` next to the connector it extends:

- **The operator the group already uses** simply adds another condition there.
- **The other operator** wraps the condition on that line in a new sub-group.

So building `State is CA` → `+AND` → `Name is Ben` → `+OR` → `Name is Nanci`
gives you:

```
[State] is equal to "California" AND ([Name] is equal to "Ben" OR [Name] is equal to "Nanci")
```

without anyone having to think about brackets. Mid-list positions offer only the
group's own operator; the last row of each group offers both, so there is exactly
one place to reach for when you want to change precedence. A group of one is
retuned rather than wrapped, and a `+OR` next to a group that is already an OR
extends it instead of nesting another.

#### Closing a strand: `AND(…)` and `OR(…)`

`+AND` and `+OR` bind *tighter* — they act on the row you clicked. To go the
other way, the last row of any group with more than one child carries a third
button showing whichever operator the group is **not** using. It brackets
everything built so far, switches the group to the other operator, and leaves a
fresh condition waiting underneath:

```
Name is B  →  +OR  →  Name is N  →  AND(…)  →  State is CA  →  +OR  →  State is LA
```

```
([Name] is equal to "B" OR [Name] is equal to "N")
AND
([State] is equal to "California" OR [State] is equal to "Louisiana")
```

Both halves are reached by typing forwards, in reading order, with no going back
to insert a group. Only one of the pair is ever shown, because the group's own
operator is already available as `+AND` / `+OR` beside it.

The fresh condition arrives as a plain sibling, not inside a group of its own — a
one-child group would render as an empty pair of brackets, and the next `+OR`
turns it into the group it was going to be anyway. If the newly bracketed group's
operator matches its parent's and neither is negated, it dissolves into the
parent instead of nesting a redundant level. `allowWrapGroup: false` removes the
button; `editor.wrapAndContinue(group, 'and' | 'or')` is the programmatic form.

### Hiding the field, and showing it again

By default the editor conceals the textarea it took over — visually hidden, but
still in the form, so it keeps posting exactly as before.

`hideTextarea: 'toggle'` keeps it hidden but adds a **Show source** button to the
footer, which puts the field back on screen. `setSourceVisible(true|false)` and
`isSourceVisible()` do the same from code, and a `source` event fires either way.

`hideTarget` widens what gets hidden — a selector, an element, or a list of them.
The usual case is the row carrying the field's label, which would otherwise be
left behind labelling nothing:

```html
<div class="row">
  <label for="conditions">Conditions</label>
  <textarea id="conditions" name="conditions"></textarea>
</div>
```

```js
KConditionsEditor.attach('#conditions', {
  hideTarget: document.querySelector('#conditions').closest('.row'),
  hideTextarea: 'toggle'      // …and let them look at it
});
```

Three things it handles for you:

- **The editor is inserted after the outermost hidden element**, not after the
  textarea. Otherwise it would be placed *inside* the row about to be hidden,
  and you would never see it.
- **The textarea is always hidden too.** If your target does not contain it —
  say you name only the label — the field is added to the list, because a raw
  JSON textarea sitting beside the builder is never what you wanted.
- **A selector that matches nothing** warns and falls back to hiding the
  textarea, rather than leaving the field on show.

`destroy()` restores everything it hid.

### Finding an editor again

A textarea carries at most one editor, and it points back at it.
`KConditionsEditor.get(textareaOrSelector)` returns the instance, or `null`, for
code that never had the value `attach()` returned — a page that attached in one
script and tears down in another. `KConditionsEditor.detach(textareaOrSelector)`
calls `destroy()` on it and returns whether there was one. The handle is also on
the element itself as `textarea.kConditionsEditor`, so `$0.kConditionsEditor`
works in devtools.

Attaching to a textarea that already has an editor **replaces** it: the old one
is destroyed first, then the new one takes the field as it stands. There is no
"same options, keep the old one" shortcut, on purpose: an options object carries
callbacks, which cannot be compared, and the field's value may have changed since
the first attach. Anything registered with `on()` on the old instance goes with
it. To reuse an existing editor rather than replace it, ask `get()` first:

```js
const editor = KConditionsEditor.get('#conditions') ||
               KConditionsEditor.attach('#conditions', options);
```

### Undo and redo

`Undo` and `Redo` sit in the footer. From the keyboard: `Ctrl`/`Cmd`+`Z` to
undo, and `Ctrl`/`Cmd`+`Shift`+`Z` **or** `Ctrl`/`Cmd`+`Y` to redo. A history entry is a
serialised document plus a cursor into a list of them — there are no inverse
operations to get wrong.

Typing is the one case that needs care. A run of keystrokes in a single field
coalesces into one entry, committed when the typing pauses (`historyIdle`,
500 ms by default), when focus leaves the field, or when anything else happens.
Without that, undo would step one character at a time, which nobody wants.
Adding a chip to a list is a discrete act and gets its own entry.

Inside a text input the shortcut is left to the browser: it has its own undo
stack there, and there is no way to ask an input whether it still has anything
left in it. The field's `input` event feeds the browser's undo back into the
document, so the two stay consistent. Everywhere else the shortcut is the
editor's.

The shortcut listens on the document and asks whether this editor holds the
keyboard — focus decides when there is any, and otherwise it falls to whichever
editor was last clicked in. That matters because a structural change rebuilds
the tree and can drop focus, and "I just clicked that, undo it" is the most
common thing anyone asks of `Ctrl`+`Z`. Several editors on a page do not all
react to one keystroke, and clicking away from every editor hands the shortcut
back to the page.

```js
editor.on('undo', doc => console.log('back to', doc));
editor.canUndo();   // → true
```

`history: false` removes the feature entirely.

### Reordering

Every row and every group carries **move up** / **move down** buttons beside its
`×`, and `Alt`+`↑` / `Alt`+`↓` anywhere inside a row does the same. These come
first and dragging is layered on the same primitive, because a drag handle is
unreachable by keyboard and unusable with a screen reader — so the buttons are
the real interface and the drag is the shortcut.

Dragging uses a grip that appears with the row's other controls. It is built on
pointer events rather than HTML5 drag-and-drop, which does not fire on touch at
all, so it works on a phone. A drop indicator marks the boundary, indented to
the level being reordered, and `Escape` cancels mid-drag.

A node moves within its own group. Moving between groups is what `+AND` / `+OR`
and `AND(…)` / `OR(…)` already do, and leaving it out of the drag is what keeps
a drop unambiguous in a nested tree.

```js
editor.moveChild(group, 0, 2);
```

`allowReorder: false` removes both; `allowDrag: false` keeps the buttons and
drops the grip.

### Seeing what a button will do

Pointing at `+AND`, `+OR`, `AND(…)`, `OR(…)` or a `×` — or reaching one by tab —
previews what the click will do. For an add button: the rows that will end up
bracketed together, the operators between them, and where the new condition
lands. For a `×`: everything it would take, brackets and `NOT` included.

The colour says which bracket. An add preview carries the hue of the bracket
being formed (AND blue, OR orange); the new condition is written in the hue of
the operator that joins it. That is what makes `AND(…)` readable: everything
currently in the group is marked blue, because it stays an AND group, while
the new condition reads `OR new condition`. A `×` preview is red.

How it is drawn is the `previewStyle` option, chosen independently of the
skin — any skin with any style:

| `previewStyle` | Looks like |
|---|---|
| `bar` *(default)* | One thin bar in the margin beside the range |
| `highlight` | A tint and outline on each row and operator (the look before 0.0.27) |
| `region` | One soft wash over the range, as wide as its widest line |
| `fade` | Everything outside the range fades back |
| `color` | Text in the range takes the hue |
| `marker` | Each row's drag grip becomes a coloured dot (`--kce-preview-marker` swaps the glyph) |

The three styles that draw in the margin (`bar`, `region`, `marker`) reserve
14px left of the rule for it in the skins with no left padding of their own;
`--kce-preview-gutter` changes that.
| `underline` | Field names, operators and AND / OR in the range are underlined |

```js
KConditionsEditor.attach('#conditions', { skin: 'prose', previewStyle: 'fade' });
editor.setPreviewStyle('underline');   // live; nothing re-renders
```

Every style paints the same set — `previewTargets()` — and both the preview and
the click read the same decision: `planAdd()` and `planWrap()` return what
*would* happen, and `addBeside()` / `wrapAndContinue()` carry it out. So no
style can disagree with another about what a button affects, and none can
drift from the behaviour. No style moves anything on screen, so the button
keeps the pointer. `skins.html` and the demo have a picker for comparing them.

This earns its place mainly in `prose`, where a group is a range of lines rather
than a box you can see, so a `×` at the end of one line gives no clue how much
sits underneath it.

> **Order is presentational.** `evalGroup` evaluates every child and
> accumulates, with no short-circuiting, so neither the result nor which
> callbacks run depends on sibling order. Reordering is for readability.

### Where the AND / OR goes

In prose, `connectorPlacement` decides where each `AND` / `OR` goes. Either way it
stays put when the row's controls appear, so the word you are about to click
doesn't move.

```
// 'below' (the default): a line of its own, under the field name — or
// under the `)` after a group
Name is equal to Ann
AND
State is equal to Florida
AND (
    …

// 'inline': just after the value — fewer lines, reads along the line
Name is equal to Ann        AND
State is equal to Florida   AND (
    …
```

`'below'` reads like a formatted query: the field names and the operators share
one edge, and `AND (` stays together. It takes a short extra line per operator.
`'inline'` takes less vertical space. Its row controls (arrows and `×`) appear
after the `AND` / `OR` with the add buttons, because they cannot sit between the
value and an operator that does not move. `editor.setConnectorPlacement('inline')`
switches live. The option only affects prose; the other skins already give each
operator a row of its own.

### Operator alignment

With `connectorPlacement: 'inline'`, a connector sits immediately after the row it follows, so
without help its position depends on how wide that row happens to be — a group
whose values read "Alabama", "California", "Florida" prints its `OR`s in three
different places.

Connectors share a column per indent level. Rows at the same indent already read
as a column, so their operators join it; a deeper group is a different thought
and keeps its own. The column is measured after layout and re-measured as an
autosizing field grows or the viewport changes, so it stays true while you type.

`alignConnectors: 'group'` narrows it to one column per group. `alignConnectors:
false` turns it off — worth doing if one very long row would drag its
neighbours' operators out to the right.

The buttons stay hidden until the pointer is on the line they belong to (or they
receive keyboard focus), and they are boxed and tinted a muted version of the
operator hue, so they never compete with the `AND` / `OR` that actually describe
the rule. Pointing at one restores the full colour.

The labels are `labels.addAnd` and `labels.addOr` if you want different words,
and the colours follow `--kce-and` / `--kce-or` through `--kce-and-muted` and
`--kce-or-muted`.

### Skins

Five treatments over the same data, chosen with the `skin` option:

| Skin | Layout | Looks like |
|------|--------|------------|
| `prose` *(default)* | flow | The rule pretty-printed — one line per condition, indented by depth, real parentheses, closing bracket on its own line |
| `equation` | tree | Bracket gutters and indentation, AND/OR between the rows, no boxes |
| `blackboard` | tree | The equation layout on a dark slate panel, chalk palette |
| `ledger` | tree | Least ink: hairline guides instead of brackets |
| `boxed` | tree | Every row a bordered card. The 0.0.1 look |

In `prose`, where a group is a range of lines rather than a box, each
bracketed group also gets a **guide**: a thin line down the left of its rows,
in the group's AND / OR colour, dashed for a `NOT` group, nesting with the
groups. Pointing at a group's AND / OR word or one of its brackets brings its
guide to full strength. The rule's own top-level AND / OR have a line too,
down the whole rule, shown only while one of them is pointed at.
`groupGuides: false` turns them off.

In the written-out skins a field, an operator or a choice value reads as a
word in the sentence, so each carries a small down chevron to say it opens a
list. It is muted at rest and takes the accent colour on hover. Boxed draws
its own. The other skins
draw a group's edges already, with brackets, hairlines or card borders.

`prose` uses a different DOM from the rest, not just different CSS — an inline
formatting context cannot indent wrapped lines, and a nested block structure
cannot put `) AND NOT (` on one line. The **flow** layout emits a flat sequence
of indented `.kce-line` elements; the **tree** layout emits nested groups. The
`skin` option picks the right one; `layout` overrides it if you are writing your
own stylesheet.

The [skins page](https://kastrack.github.io/kConditionsEditor/skins.html)
renders all five side by side, live (`docs/skins.html` in the repo).

### Theming

**Set `--kce-accent` to your own brand colour.** The default blue is a
placeholder, not the component's identity: it is what hover, focus and the
active states turn, so left alone in a green host it is a colour that appears
nowhere else on the page. One line does it:

```css
.kce { --kce-accent: #2e7d4f; --kce-accent-soft: #e6f2ea; }
```

Every colour and metric is a CSS custom property on `.kce`:

```css
.kce {
  --kce-accent: #7c3aed;   /* focus, links, active states */
  --kce-accent-soft: …;    /* hover tints behind them      */
  --kce-field:  #101820;   /* field names                 */
  --kce-op:     #7a8290;   /* operator labels             */
  --kce-value:  #1a5f8a;   /* literal values              */
  --kce-and:    #2f6fd0;   /* AND connectors              */
  --kce-or:     #a8560c;   /* OR connectors and NOT       */
  --kce-and-muted: …;      /* +AND button (derived)       */
  --kce-or-muted:  …;      /* +OR button  (derived)       */
  --kce-rule:   #b6bdc8;   /* hairline guides             */
  --kce-paren:  #59636f;   /* brackets in the prose skin  */
  --kce-radius: 12px;
  --kce-indent-step: 2.2em;
}
```

Light and dark are both handled; pass `theme: 'light' | 'dark'` (or set
`data-kce-theme`) to pin one.

### Inside someone else's form

The editor is usually embedded in a form that styles its own inputs, and a
rule like `.dialog input[type=text] { width: 24rem; height: 42px }` would
otherwise reach the editor's value slots and turn them into full-width boxes.
The stylesheet pins the box metrics the editor depends on — width, height,
margins, radius, shadow — at a specificity above element and class-scoped host
rules, so those are ignored inside `.kce`. A host rule scoped by an **ID**
(`#properties input { … }`) still outranks it; exclude the editor there:

```css
#properties input:not(.kce *) { width: 24rem; }
```

The editor is built for narrow hosts as well as wide pages. **A row is one
line**: its arrows, × and the AND / OR after it never drop below it. When the
line is short the row gives up width — its value first, down to a floor
(enough to type in, or to read a date in), then the field and operator names,
which ellipsis but keep a readable few letters. A value of fixed size
(`between`, a date range) shrinks to stay on its line; only an "is one of" tag
list wraps, inside its own box, with the field, operator and controls on its
first line. If a row still cannot fit, the line scrolls sideways rather than
anything overlapping — in practice below about 480px.

The `controls` option decides when the row controls are shown. With
`'hover'` (the default), the add buttons after a row take no room until they
are needed: in prose they appear after the AND / OR when the line has space,
or as a small strip just below it, and nothing moves when they do. With
`'always'` everything is shown at rest and keeps its room. A screen with no
hover gets `'always'` whatever the option says.

```js
KConditionsEditor.attach('#conditions', { controls: 'always' });
editor.setControls('hover');   // live
```

## Testing

```bash
npm test              # JavaScript, node --test, no dependencies
npm run test:php      # PHP, no dependencies
npm run test:browser  # real Chromium; needs `npx playwright install chromium` once
npm run test:all      # all three

composer install && vendor/bin/phpunit    # the PHPUnit suites, if you have Composer
```

`tests/fixtures/cases.json` holds 34 shared evaluation cases, 34 shared SQL cases and 25
shared `describe()` cases. The JavaScript and PHP suites both run that file — SQL and both
describe renderings are compared character for character — so the two runtimes agree by
construction, and a port to a new language is finished when it passes them too.

`tests/browser/` drives real Chromium with real pointer, focus and keyboard events, and
judges results by what is painted rather than by what class was applied. That is where
hover, drag, undo, the previews, the skins and the built bundles are covered.
`npm run test:browser` runs every script in the directory and fails if any is red; pass a
substring to run a subset (`node tests/browser/run.js undo`).

Why the project is built this way, decision by decision, is in [notes/](notes/)
— `design-record.md` for the running summary, one file per interesting version for the
detail. [CLAUDE.md](CLAUDE.md) is the orientation document for anyone (or anything)
picking the code up.
