Installation

Browser — one file each

<link rel="stylesheet" href="dist/k-conditions.min.css">
<script src="dist/k-conditions.min.js"></script>

The bundle is the editor, the evaluator and the SQL builder together, with every skin — about 21 KB gzipped. It sets both KConditions and KConditionsEditor on the global, so everything below applies unchanged.

Browser — the sources, no build step

<link rel="stylesheet" href="src/k-conditions-editor.css">
<link rel="stylesheet" href="src/k-conditions-skins.css">

<script src="src/k-conditions-evaluator.js"></script>
<script src="src/k-conditions-sql.js"></script>  <!-- optional -->
<script src="src/k-conditions-editor.js"></script>

The evaluator must load first — the editor uses its operator metadata and its describe() function. The skins stylesheet is required for every skin except boxed, and the SQL builder only if you want SQL output. All three scripts are UMD, so they also work through a bundler or under Node.

npm

npm install @kastrack/conditions-editor
const KConditions = require('@kastrack/conditions-editor');
// or, in the browser bundle:
import KConditionsEditor from '@kastrack/conditions-editor/editor';
import '@kastrack/conditions-editor/editor.css';

Composer

Building a rule

A rule grows from the logic word rather than from a generic "add row" button. Every insertion point carries a +AND or +OR beside the connector it extends:

  • The operator the group already uses adds another condition at that point.
  • The other operator wraps the condition on that line in a new sub-group carrying it.

So State is CA → +AND → Name is Ben → +OR → Name is Nanci produces State is CA AND (Name is Ben OR Name is Nanci), without anyone having to think about brackets.

Mid-list positions offer only the group's own operator — the one that reads naturally next to the connector already printed there. The last row of each group offers both, so there is exactly one place to reach for when changing precedence. Two conveniences keep the tree from growing needless levels: a group of one child is retuned rather than wrapped, and clicking +OR beside a group that is already an OR extends it instead of nesting another inside it.

AND(…) and OR(…) — closing a strand

+AND and +OR bind tighter: they act on the row you clicked. To go the other way, the last row of any group holding more than one child carries a third button showing whichever operator the group is not using. It brackets everything built so far, switches the group to the other operator, and leaves a fresh condition waiting underneath.

So Name is B → +OR → Name is N → AND(…) → State is CA → +OR → State is LA produces (Name is B OR Name is N) AND (State is CA OR State is LA) — both halves typed forwards, in reading order, with no going back to insert a group. Only one of the pair is ever shown, since the group's own operator is already offered as +AND / +OR beside it.

The fresh condition arrives as a plain sibling rather than inside a group of its own: a one-child group renders as an empty pair of brackets, and the next +OR turns it into the group it was going to be anyway. If the newly bracketed group's operator matches its parent's and neither is negated, it dissolves into the parent instead of nesting a redundant level. Turn the button off with allowWrapGroup: false, or drive it from code with editor.wrapAndContinue(group, 'and').

The buttons stay hidden until the pointer is on the line they belong to, or until they take keyboard focus. They are boxed and tinted a muted version of the operator hue, so they never compete with the AND / OR that actually describe the rule; pointing at one restores the full colour.

Labels come from labels.addAnd and labels.addOr, and the colours are derived from --kce-and / --kce-or via --kce-and-muted and --kce-or-muted.

Values survive an operator change wherever the slot still means the same thing — switching is equal to for matches regex keeps what you typed. A value only drops when it genuinely cannot fit the new slot, such as free text moving into a date operator that cannot parse it.

Hiding the field

By default the editor conceals the textarea it took over — visually hidden but still in the form, so it keeps posting exactly as before. hideTextarea: 'toggle' keeps it hidden and adds a Show source button to the footer that puts it back on screen. 

KConditionsEditor.attach('#conditions', { hideTextarea: 'toggle' });

editor.setSourceVisible(true);   // the same from code
editor.isSourceVisible();        // → true
editor.on('source', ({ visible }) => …);
Not to be confused with View source, which debug: true adds: that one shows the document the editor is generating, this one shows the field it is written into. Both label sets are overridable through labels (revealField / concealField here, viewSource / hideSource there).

hideTarget

Often the textarea is not the only thing that should disappear — the row carrying its label would otherwise be left behind labelling nothing. hideTarget takes a CSS selector, an element, or a list of either: 

<div class="row">
  <label for="conditions">Conditions</label>
  <textarea id="conditions" name="conditions"></textarea>
</div>
KConditionsEditor.attach('#conditions', {
  hideTarget: document.querySelector('#conditions').closest('.row'),
  hideTextarea: 'toggle'
});

Three things it takes care of:

  • The editor is inserted after the outermost hidden element, not after the textarea — otherwise it would be placed inside the row about to be hidden, and you would never see it.
  • The textarea is always hidden too. If your target does not contain it — naming only the label, say — the field is added to the list, because a raw JSON textarea beside the builder is never the intent.
  • A selector matching nothing warns and falls back to hiding the textarea, rather than leaving the field on show.

destroy() restores everything it hid.

Finding an editor again

A textarea carries at most one editor, and it points back at it. KConditionsEditor.get(textareaOrSelector) returns the instance, or null, for code that never had the value attach() returned. KConditionsEditor.detach(textareaOrSelector) calls destroy() on it and returns whether there was one. The handle is also on the element as textarea.kConditionsEditor, so $0.kConditionsEditor works in devtools.

Attaching to a textarea that already has an editor replaces it: the old one is destroyed first, then the new one takes the field as it stands. There is no "same options, keep the old one" shortcut, on purpose: an options object carries callbacks, which cannot be compared, and the field's value may have changed since the first attach. Anything registered with on() on the old instance goes with it. To reuse an existing editor rather than replace it, ask get() first. 

const editor = KConditionsEditor.get('#conditions') ||
               KConditionsEditor.attach('#conditions', options);

Undo and reordering

Undo and redo

Undo and Redo sit in the footer. From the keyboard: Ctrl/Cmd+Z to undo, and Ctrl/Cmd+Shift+Z or Ctrl/Cmd+Y to redo. A history entry is just a serialised document, with a cursor into a list of them — there are no inverse operations to get wrong, and undo is a reload of a state the editor has already been in.

Typing is the one case that needs care. A run of keystrokes in a single field coalesces into one entry, committed when the typing pauses (historyIdle), when focus leaves the field, or when anything else happens. Without that, undo would step one character at a time. Adding a chip to a list is a discrete act and gets its own entry.

Inside a text input the shortcut is the browser's. It has its own undo stack there, and there is no reliable way to ask an input whether it still has anything left in it — so the editor stays out of the way, and the field's input event feeds the browser's undo back into the document. Everywhere else, the shortcut is the editor's.

The shortcut listens on the document and asks whether this editor holds the keyboard: focus decides when there is any — only one editor can contain it — and otherwise it falls to whichever editor was last clicked in. A structural change rebuilds the tree and can drop focus, and "I just clicked that, undo it" is the most common thing anyone asks of Ctrl+Z, so an element-scoped listener would go quiet at exactly the wrong moment. Several editors on one page do not all react to one keystroke, and clicking away from every editor hands the shortcut back to the page. 

editor.on('undo', doc => console.log('back to', doc));
editor.canUndo();   // → true
editor.redo();

Move up, move down, and drag

Every row and every group carries move up / move down buttons beside its ×, and Alt+↑ / Alt+↓ anywhere inside a row does the same thing. These come first and the drag is layered on the same primitive, because a drag handle is unreachable by keyboard and unusable with a screen reader: the buttons are the real interface and dragging is the shortcut.

Dragging uses a grip that appears with the row's other controls. It is built on pointer events rather than the HTML5 drag-and-drop API, which does not fire on touch at all, so it works on a phone. A drop indicator marks the boundary the row will land on, indented to the level being reordered, and Escape cancels mid-drag.

A node moves within its own group. Moving between groups is what +AND / +OR and AND(…) / OR(…) already do, and leaving it out of the drag is what keeps a drop unambiguous in a nested tree. 

editor.moveChild(group, 0, 2);   // the primitive both interfaces use

Seeing what a button will do

Pointing at +AND, +OR, AND(…), OR(…) or a × — or reaching one by tab — previews what the click will do. For an add button: the rows that will end up bracketed together, the operators between them, and where the new condition lands. For a ×: everything it would take, brackets and NOT included.

The colour says which bracket. An add preview carries the hue of the bracket being formed; the new condition is written in the hue of the operator that joins it. That is what makes AND(…) readable: everything in the group is marked blue, because it stays an AND group, while the new condition reads OR new condition. A × preview is red.

How it is drawn is the previewStyle option, independent of the skin:

previewStyleLooks like
bar (default)One thin bar in the margin beside the range.
highlightA tint and outline on each row and operator — the look before 0.0.27.
regionOne soft wash over the range, as wide as its widest line.
fadeEverything outside the range fades back.
colorText in the range takes the hue.
markerEach row's drag grip becomes a coloured dot; --kce-preview-marker swaps the glyph.
underlineField names, operators and AND / OR in the range are underlined.
 
KConditionsEditor.attach('#conditions', { skin: 'prose', previewStyle: 'fade' });
editor.setPreviewStyle('underline');   // live; nothing re-renders
Every style paints the same set, and the preview and the click read the same decision. previewTargets() decides what is marked; the styles only decide how. planAdd() and planWrap() return what would happen; addBeside() and wrapAndContinue() carry it out. So no style can disagree with another, or drift from the behaviour. No style moves anything on screen, so the button keeps the pointer. The skins page has a picker for comparing them.

This earns its place mainly in prose, where a group is a range of lines rather than a box you can see, so a × at the end of one line gives no indication how much sits underneath it.

Where the AND / OR goes

In prose, connectorPlacement decides where each AND / OR goes. Either way it stays put when the row's controls appear, so the word you are about to click doesn't move. 

// "below" (the default): a line of its own, under the field name — or
// under the `)` after a group
Name is equal to Ann
AND
State is equal to Florida
AND (
    …

// "inline": just after the value — fewer lines, reads along the line
Name is equal to Ann        AND
State is equal to Florida   AND (
    …

"below" reads like a formatted query: the field names and the operators share one edge, and AND ( stays together. It takes a short extra line per operator. "inline" takes less vertical space. Its row controls (arrows and ×) appear after the AND / OR with the add buttons, because they cannot sit between the value and an operator that does not move. editor.setConnectorPlacement("inline") switches live. The option only affects prose; the other skins already give each operator a row of its own.

Operator alignment

With connectorPlacement: "inline", a connector sits immediately after the row it follows, so without help its position depends on how wide that row happens to be — a group whose values read "Alabama", "California", "Florida" prints its ORs in three different places, which is the wrong look for a layout whose whole argument is that a rule should read like an equation.

Connectors share a column per indent level: rows at the same indent already read as a column, so their operators join it, while a deeper group is a different thought and keeps its own. The column is measured after layout and re-measured as an autosizing field grows or the viewport changes, so it stays true while you type. alignConnectors: "group" narrows it to one column per group; false turns it off, which is worth doing if one very long row would drag its neighbours' operators out to the right.

Sibling order is presentational. The evaluator walks every child of a group and accumulates, with no short-circuiting, so neither the result nor which callbacks run depends on the order. This is for readability — worth knowing before relying on it for anything else.

Skins and theming

The editor ships five visual treatments over the same data. Load the skins stylesheet alongside the base one — it is required for everything except boxed — and name the skin you want: 

<link rel="stylesheet" href="src/k-conditions-editor.css">
<link rel="stylesheet" href="src/k-conditions-skins.css">

SkinLayoutWhat it looks like

equationtreeBracket gutters and indentation, AND/OR on their own lines between rows. No boxes.

In prose, each bracketed group also gets a guide: a thin line down the left of its rows in the group's AND / OR colour, dashed for a NOT group, nesting with the groups, so any row can be traced to the group it belongs to. Pointing at a group's AND / OR word or one of its brackets brings its guide to full strength. The rule's own top-level AND / OR have a line too, down the whole rule, shown only while one of them is pointed at. groupGuides: false turns them off.

In the written-out skins a field, an operator or a choice value reads as a word in the sentence, so each carries a small down chevron to say it opens a list. Boxed draws its own.

Two layouts, not just two stylesheets

prose uses a different DOM from the others, because CSS alone cannot produce it: an inline formatting context cannot indent wrapped lines, and a nested block structure cannot put ) AND NOT ( on one line. The flow layout renders a flat sequence of .kce-line elements indented by depth; the tree layout renders nested .kce-group boxes. The skin option picks the right one for you.

Theming

Set --kce-accent to your own brand colour. The default blue is a placeholder, not the component's identity — it is what hover, focus and the active states turn, so in a green host it is a colour that appears nowhere else on the page: 

.kce { --kce-accent: #2e7d4f; --kce-accent-soft: #e6f2ea; }

Every colour and metric is a custom property on .kce, so a skin can be retinted without touching the stylesheet: 

.kce {
  --kce-accent: #7c3aed;   /* focus, links, active states */
  --kce-accent-soft: …;    /* hover tints behind them      */
  --kce-field:  #101820;   /* field names                 */
  --kce-op:     #7a8290;   /* operator labels             */
  --kce-value:  #1a5f8a;   /* literal values              */
  --kce-and:    #2f6fd0;   /* AND connectors              */
  --kce-or:     #a8560c;   /* OR connectors and NOT       */
  --kce-rule:   #b6bdc8;   /* hairline guides             */
  --kce-paren:  #59636f;   /* brackets in the prose skin  */
  --kce-radius: 12px;
  --kce-indent-step: 2.2em;
}

Light and dark are both defined. The editor follows prefers-color-scheme unless you pin it with the theme option (or data-kce-theme on the root). blackboard is deliberately dark in both.

Inside someone else's form

The editor is usually embedded in a form that styles its own inputs. The stylesheet pins the box metrics the editor depends on — width, height, margins, radius, shadow — above element and class-scoped host rules, so a dialog's .form input[type=text] { width: 24rem } does not reach the value slots. A host rule scoped by an ID still outranks it; exclude the editor there with #properties input:not(.kce *).

A row is one line: its arrows, × and the AND / OR after it never drop below it. When the line is short the row gives up width — its value first, down to a floor, then the field and operator names, which ellipsis but keep a readable few letters. between and date ranges shrink to stay on their line; only an "is one of" tag list wraps, inside its box, with everything else on its first line. A row that still cannot fit makes the line scroll sideways rather than overlap.

The controls option decides when the row controls are shown. With "hover" (the default) the add buttons take no room until needed — in prose they appear after the AND / OR, or as a small strip just below it when the line is full — and nothing moves when they do. With "always" everything is shown at rest. A screen with no hover gets "always" regardless.

Upgrading from 0.0.1? The default changed from boxed to prose. Pass skin: 'boxed' to keep the old appearance exactly; nothing about the document format changed.

Field definitions

{
  name: 'dob',                 // required — the key looked up in your data
  label: 'Date of Birth',      // shown in the UI; defaults to name
  type: 'date',                // text | number | date | boolean | enum
  column: 'c.date_of_birth',   // SQL column name; defaults to name
  choices: [...],              // for enum fields; strings or {value, label}
  operators: [...],            // explicit operator list, overrides the type default
  operatorGroups: [...],       // or pick whole groups: ['date', 'existence']
  excludeOperators: [...],     // remove specific operators from whatever was chosen
  values: ['literal','field'], // which value sources are offered
  comparableWith: [...],       // which fields this one may be compared against
  placeholder: '…',
  input: { min: 0, max: 100, step: 1, type: 'datetime-local' }
}

Operator selection

With no operators the field gets the groups its type implies: text → equality, alphanumeric, existence; number → equality, arithmetic, existence; date → date, existence; boolean → boolean, existence; enum → equality, alphanumeric, existence. Entries in operators may be a bare operator name or "group:date" to pull in a whole group.

Choices

A field's choices — and a custom values operator's values — may be written three ways. All three mean the same thing: the first item is stored in the document, the second is what the user sees. 

choices: ['Florida', 'Texas']
choices: [{ value: 'FL', label: 'Florida' }, { value: 'TX', label: 'Texas' }]
choices: { FL: 'Florida', TX: 'Texas' }        // an associative map

Labels are used in the dropdowns, in the collapsed summary and in describe(), so a rule reads [State] is equal to "Florida" while the document stores "FL".

Except where the operand is not a choice. contains, does not contain, starts with, ends with, matches regex and does not match regex take a fragment or a pattern, not one of the values. On those the editor shows a free text box instead of the dropdown, and describe() prints what was typed rather than swapping it for a label: 

[State] is equal to "Florida"     ← eq: a whole value, so the label
[State] contains "FL"             ← contains: a substring, left alone

Operators carry this as valueFromChoices in their metadata (absent means true). A custom operator whose operand is a fragment should set it false to get the same treatment.

Comparing against another field

A value can be a literal or a pointer at another field, and where both are possible the editor shows a small Value / Field selector beside the value. That selector is off by default — it costs a control on every row that has a value, to buy a feature most rules never use. 

KConditionsEditor.attach('#conditions', { fields, allowFieldValues: true });

Or leave it off and opt in one field at a time: naming comparableWith on a field is read as asking for it, so it works with the global setting untouched. comparableWith: false still wins, so a field can opt out even with the global on. And a document that already holds a field reference always keeps its selector, whatever the settings say — otherwise there would be no way back to a literal.

Changed in 0.0.21. This used to be on by default, so any field without its own comparableWith silently became comparable with every other field of its type and carried the selector. If you were relying on that, set allowFieldValues: true.

comparableWith

Controls which other fields may appear in the Field value dropdown.

ValueMeaning
omittedOther fields of the same type.
false or []No field comparison — literals only.
'*'Every other field.
['billing_email']Exactly the named fields.
['type:date']Every field of that type.
['group:contact']Every field carrying group: 'contact'.

Entries combine, so ['billing_email', 'type:date'] is valid.

Custom operators

Custom operators are passed to the editor and copied into the document whenever they are actually used, so the JSON stays self-contained. Two kinds.

A fixed set of values

operators: {
  is_gulf_state: {
    kind: 'values',
    label: 'is a Gulf state',
    match: 'in',                 // or 'not_in'
    arity: 0,                    // 0 = fixed list, no value input shown
    values: ['Florida', 'Louisiana', 'Texas', 'Mississippi'],
    appliesTo: ['state']         // editor-only: which fields offer it
  }
}

With arity: 1 the list becomes the choices offered in the editor and the selected value is stored on the condition instead.

A host function

operators: {
  email_is_unique: {
    kind: 'callback',
    label: 'is not already registered',
    arity: 0,
    appliesTo: ['email'],
    availableIn: ['server'],
    callbacks: {
      php:    { class: '\\App\\Rules\\Email', method: 'isUnique', static: true },
      js:     { function: 'emailIsUnique' },
      python: { module: 'app.rules', function: 'email_is_unique' }
    },
    policy: {
      unresolved: { client: 'skip', server: 'error', '*': 'error' },
      error:      { client: 'skip', '*': 'error' }
    }
  }
}

The callback receives (fieldValue, args, context) and returns a boolean — or the SKIP sentinel to opt out at runtime. appliesTo is stripped when the operator is written into the document.

SQL output

The same rule can be rendered as a SQL boolean expression — the part that goes after WHERE. Load the SQL builder and you have SQL: 

<script src="src/k-conditions-sql.js"></script>
KConditions.toSql(document, { dialect: 'mysql' });
// → `email` = 'a@b.c' AND `dob` < '1980-01-01'
column is optional. A field's name is used as the column name unless you say otherwise, so a schema whose columns already match your field names needs no mapping at all — and a field the builder has never been told about still resolves to its own name. Give a field a column only where the two differ. 
{ name: 'dob', label: 'Date of Birth', type: 'date', column: 'c.date_of_birth' }

The resolution order per field is column → sql → name, and the builder's columns option (a plain { field: column } map) overrides all three — useful when one document has to run against two schemas. Entries in fields may also be bare strings when all you want is the type defaults. 

const { sql, params } = editor.getSql({ dialect: 'mysql' });
// or, standalone:
KConditions.toSql(document, { dialect: 'mysql', fields });
use function Kastrack\ConditionsEditor\toSql;

$where = toSql($document, ['dialect' => 'mysql', 'fields' => $fields]);
$rows  = $db->query("SELECT * FROM contacts c WHERE $where");

Where to generate it

Both places are supported, and which is right depends on what your endpoint already accepts.

  • Server-side, from the document. The browser posts the JSON and the server builds the SQL. Use this when your endpoint receives a rule and you would rather not widen it into accepting SQL.
  • Client-side, into the textarea (output: 'sql'). Use this when the field already accepts SQL. If a person could previously type status = 'x' OR 1=1 into that box, a builder writing a nicer expression into it adds no attack surface: the trust boundary is where it always was, and whatever sanitising and sandboxing you do on the way in still applies.
The one combination to avoid is the middle ground — an endpoint that today receives JSON and starts executing client-supplied SQL because it is convenient. That is a new trust boundary; keep posting the document and build the SQL on the server. Use parameters: true wherever your driver supports placeholders, in either mode.

It is a translation, not the evaluator

SQL has three-valued logic and the evaluator does not, so a row-for-row match is not guaranteed. The choices made here:

  • Negative operators are null-safe by default: col <> 'x' becomes (col IS NULL OR col <> 'x').
  • is_empty covers both NULL and ''.
  • date_eq becomes a half-open day range, which is portable and index-friendly.
  • The relative date operators resolve against now at generation time rather than emitting CURRENT_DATE, so a saved query keeps the dates it was built with.
  • LIKE patterns escape %, _ and the escape character itself, and carry an explicit ESCAPE clause.

Operators with no SQL

A callback operator cannot be translated. Give it an sql template and it can be: 

email_is_unique: {
  kind: 'callback',
  sql: 'NOT EXISTS (SELECT 1 FROM blocked b WHERE b.email = {field})'
}

{field} is the quoted column, {0}/{1} the rendered values, {values} the comma-separated list. Without a template the operator falls to the unresolved policy, so {"unresolved": {"sql": "skip"}} drops it from the WHERE clause and leaves it to be evaluated in code. Regular expressions are unsupported in SQL Server and need a UDF in SQLite; those fall to unsupportedPolicy.

Writing SQL into the textarea

output: 'sql' puts the expression in the textarea instead of the JSON. It defaults to 'json', so you opt in. SQL does not parse back into a rule, so the editor needs somewhere to keep the document if the rule is to survive a reload — two ways, depending on whether you can add a field.

You can add a hidden field

<textarea name="conditions"></textarea>
<input type="hidden" name="conditions_doc">
KConditionsEditor.attach('[name=conditions]', {
  output: 'sql',
  documentInput: '[name=conditions_doc]',
  sql: { dialect: 'mysql' },
  fields
});

You cannot — it is an existing SQL field and that is all there is

KConditionsEditor.attach('#existing-sql-field', {
  output: 'sql',
  documentInComment: true,   // the rule rides along in a trailing SQL comment
  hideTextarea: false,       // let people see the SQL it writes
  sql: { dialect: 'mysql' },
  fields
});
(`c`.`full_name` REGEXP '^ben' AND `a`.`state_code` IN ('FL', 'TX'))
/* kconditions:1.0 {"version":"1.0","operators":{},"root":{…}} */

The comment trails the expression — in a field someone can see, the SQL is the point and the document is baggage. It is a no-op to the database and the editor reads the rule back out of it, so a single field round-trips. Two caveats: anything that strips comments before storing the SQL loses the rule (the SQL still works, the builder just reopens empty), and hand-edits to the generated SQL are overwritten the next time someone touches the builder — so if people will switch between typing SQL and using the builder, keep the raw SQL somewhere the editor does not own.

The field already holds something the editor cannot read

SQL written by hand, say, with no document beside it. The editor does not replace it: the field keeps its content, byte for byte, until the first change to the rule, so an untouched form submits exactly what it loaded. Meanwhile a notice above the rule shows the original text, with a Dismiss button, so the rule can be rebuilt while reading it (labels preservedText and preservedDismiss). editor.preserved is { text } or null, editor.pristine says whether the field is still untouched, and the change payload carries pristine too. Opening the editor, changing skin or theme and re-attaching do not count as changes; adding, editing, undoing and setDocument() do. There is no parser: the editor never guesses what a hand-written expression meant.

Debugging

debug: true adds a View source button to the footer. It opens a tabbed panel showing the document, the generated SQL — with its bound parameters, skipped operators and warnings — and the plain-English summary with any validation problems, each with a copy button. 

KConditionsEditor.attach('#conditions', {
  fields,
  debug: window.APP_DEBUG === true,
  sql: { dialect: 'mysql' }
});
Off by default, and worth keeping that way in production: the panel exposes your SQL column names and the whole rule to anyone looking at the page.

The document format

{
  "version": "1.0",
  "generator": "kConditionsEditor/0.0.1",
  "operators": { /* custom operators used by this rule */ },
  "root": {
    "type": "group",
    "operator": "and",
    "negate": false,
    "children": [
      {
        "type": "condition",
        "field": "name",
        "operator": "regex",
        "values": [{ "source": "literal", "value": "^ben" }]
      }
    ]
  }
}

A value node is either { "source": "literal", "value": … } or { "source": "field", "field": "other_field" }. An empty children array means "no conditions", which evaluates to the evaluator's emptyResult (true by default).

The full specification is in SPEC.md, with a machine-readable JSON Schema.

Comparison rules

  • Equality compares numerically when both sides look numeric, otherwise as strings. Arrays compare structurally.
  • Arithmetic comparisons are false when either side is not numeric — they never throw.
  • Dates accept YYYY, YYYY-MM, YYYY-MM-DD, full ISO timestamps, epoch milliseconds and native date objects. A partial date expands to its earliest UTC instant, so is before 1980 means before 1980-01-01T00:00:00Z.
  • date_eq and date_is_today compare UTC calendar days; everything else compares instants.
  • String comparison is case-sensitive unless the evaluator is given caseInsensitive: true.
  • Regex values are bare patterns without delimiters. Stick to the common subset — anchors, classes, quantifiers, groups — for cross-language parity.

Failure policies

Two things can go wrong with a condition: the operator cannot be resolved in this runtime, or evaluating it throws. Each is governed by a policy resolving to skip, true, false or error.

Where a policy comes from

  1. condition.policy.unresolved / .error
  2. operators[name].policy.unresolved / .error
  3. the evaluator's unresolvedPolicy / errorPolicy option — both default to error

Context labels

A policy may be a bare string, or a map keyed by context label. Labels are matched in this order: each entry of profiles, then environment, then runtime, then "*" / "default". 

{ "client": "skip", "server": "error", "js": "skip", "*": "error" }

That is why the same rule works in a browser and under Node on a server: the two evaluators are constructed with different environment values and pick different branches.

What skipping means

A skipped condition behaves as though it were never in the document. It is dropped from its parent's children and the siblings decide the group. If every child of a group is skipped, the group is skipped too and drops out of its own parent, and so on. If the whole document ends up skipped, the evaluator returns its emptyResult. A skipped condition can never turn an OR true.

Skipped nodes are listed in the detailed result, so a server-side pass can see exactly what the client deferred.

JavaScript / Node SDK

The evaluator is one file with no dependencies, src/k-conditions-evaluator.js, and the same file runs in the browser and under Node. The SQL builder, src/k-conditions-sql.js, is optional and attaches toSql() to it. 

const K = require('@kastrack/conditions-editor');

// One-shot
const ok = K.evaluate(document, data, { environment: 'server' });

// Reusable, with your own operators registered
const evaluator = new K.Evaluator({
  environment: 'server',
  unresolvedPolicy: 'error',
  now: () => Date.now(),
  caseInsensitive: false,
  trace: true
});

evaluator.registerOperator('email_is_unique', async () => { /* … */ });

const details = evaluator.evaluateDetailed(document, data);
// { result, skipped, errors, trace, allSkipped }
Operators are synchronous. An operator that returns a promise will be treated as truthy. Resolve anything asynchronous before evaluating and pass the answer in as a field, or register a synchronous operator that reads from a cache you populated first.

PHP SDK

The PHP SDK is in sdk/php: PSR-4 under Kastrack\ConditionsEditor, PHP 8.1+, no dependencies. Install it with Composer, or require its autoload.php directly (see Installation). 

use Kastrack\ConditionsEditor\Evaluator;
use function Kastrack\ConditionsEditor\evaluate;

// One-shot — the document may be the raw POSTed JSON string
$ok = evaluate($_POST['conditions'], $submission, ['environment' => 'server']);

// Reusable
$evaluator = new Evaluator([
    'environment' => 'server',
    'now' => new DateTimeImmutable('2026-08-27T12:00:00Z'),
]);

$evaluator->registerOperator(
    'email_is_unique',
    fn (mixed $value, array $args, array $ctx): bool => !User::emailExists($value)
);

$details = $evaluator->evaluateDetailed($document, $submission);
$details->result;    // bool
$details->skipped;   // array
$details->errors;    // array

Options match the JavaScript SDK key for key, with runtime defaulting to "php" and an extra container option — any object with a get() method — used to build instances for non-static manifest callbacks. $data may be an array or an object, and dot paths reach into nested arrays and public properties.

An operator may return Skip::instance() to opt out at runtime.

The result hook

Every SDK entry point takes an optional trailing callable. When supplied, the SDK returns that callable's return value instead of the boolean. It receives the original call's arguments, then the computed result, then the details. 

const outcome = K.evaluate(document, data, options,
  (document, data, options, result, details) => {
    metrics.increment(result ? 'rule.pass' : 'rule.fail');
    return { ok: result, deferred: details.skipped.map(s => s.operator) };
  });
$outcome = evaluate($document, $data, $options,
    function (array $document, array $data, array $options, bool $result, $details) {
        Log::info('rule evaluated', ['result' => $result, 'skipped' => $details->skipped]);

        return new RuleOutcome($result, $details->skipped);
    });

Evaluator::evaluate() accepts the hook as its third argument, where the options were supplied to the constructor instead.

Showing a rule to a reader

A stored document is JSON. To put it in front of someone — a confirmation page, an audit log, an email — both SDKs render it as a sentence. 

KConditions.describe(document, { fields });
// [State] is equal to "Florida"

KConditions.describeHtml(document, { fields });
// <span class="kcd"><strong class="kcd-field">State</strong> <span class="kcd-op">is equal to</span> <span class="kcd-value">Florida</span></span>
use function Kastrack\ConditionsEditor\{describe, describeHtml};

describe($document, ['fields' => $fields]);
describeHtml($document, ['fields' => $fields]);

The two say the same thing: the brackets and quotes that mark a field and a value in plain text become a bold field and an underlined value in HTML. Both take the same options — fields (for labels and choice labels), operators (custom operator labels) and emptyText — and both walk the document with the same function, so they cannot disagree about bracketing, NOT placement or which label won. Only the leaf formatting differs.

describeHtml() always escapes, and there is no way to turn that off. A document is client-supplied input — field labels, values and emptyText all come from somewhere you do not control — so <img src=x onerror=…> in a value comes back as text, every time. That is also why it is a separate function rather than a flag on describe(): the call site says out loud that it is producing markup.

A longer one, rendered live below — this page loads src/k-conditions-editor.css and nothing else, and has no editor anywhere on it:

(Name is equal to A AND NOT (State is equal to Florida OR State is equal to Texas))

In the editor

summaryHtml: true renders the collapsed summary with describeHtml() instead of plain text, so the field names and values in the header get the same treatment. The editor also exposes both directly, using its own fields and operators so you need not pass them again. 

const editor = KConditionsEditor.attach('#conditions', { fields, summaryHtml: true });

editor.describe();      // string
editor.describeHtml();  // string of HTML

Security

Condition documents are untrusted input. They arrive from a browser. Treat them the way you treat any other posted field.
  • Callback dispatch is off by default. Resolving a function name out of a JSON document is arbitrary dispatch, so every SDK looks in its own registry first and ignores the callbacks block entirely unless you set allowManifestCallbacks: true. Narrow it further with callbackAllowList. Registering your callables with registerOperator() is the recommended route and needs no opt-in.
  • Validate against your own field list before evaluating, so a tampered document cannot reference fields you never offered: validateDocument(doc, { fields }).
  • Regular expressions come from the document. A pathological pattern can be expensive to run. If documents can be authored by people you do not trust, drop regex from the operator lists, or evaluate behind a timeout.
  • Never let a client-side result stand in for the server's. The point of the skip policy is to pre-check what can be pre-checked; the server still has to evaluate the whole rule.

Porting to another language

The document format is deliberately small. A port needs: a recursive walk over group and condition nodes, the operator table, the four coercion helpers (toNumber, toDate, toBool, toList), and the policy resolver.

Then point it at tests/fixtures/cases.json. Those fixtures are the contract — the JavaScript and PHP suites run the identical file, and a port that passes them agrees with both.
