# Undo and drag-to-reorder — shipped in 0.0.10

This file was the pre-build assessment (written 2026-09-03 against 0.0.8). Both
features were built the same day in 0.0.10. Kept as a record of what the
estimate said versus what actually happened.

## What was built

All three of Ben's choices were the recommended options:

- Undo: **structural changes plus coalesced text edits** (not structural-only).
- Reordering: **move up/down buttons plus drag in every skin**, prose included.
- Drag scope: **within a node's own group only**.

## How the estimate held up

| Predicted | Actual |
|---|---|
| Mutation API first, ~2 hours mechanical | Correct, and it did make both features smaller |
| Undo ~1 day, low risk | Correct. The states-list model needed no inverse ops |
| Typing granularity is "the fiddly part" | Overstated — burst key + idle timer + flush-on-anything-else was straightforward |
| Focus/scroll after re-render is "another chunk of work" | Overstated once ids became **positional**. See below |
| Ctrl+Z fights the browser inside inputs | Correct, and the predicted rule (defer inside INPUT/TEXTAREA) is what shipped |
| Drag in flow needs a line→(group,index) map | Correct, and it was the bulk of the drag work |
| Drag handle cuts against the quiet-until-hovered direction | Solved by giving the grip the same reveal treatment as everything else |
| HTML5 DnD does not work on touch | Correct. Pointer events + `touch-action: none`, verified with real touch pointers |

## Decisions worth keeping

**Positional node ids.** `assignPathIds(root, 'r')` at the top of `render()`
makes a node's id its path (`r.0.1`). Ids were already stripped from the output,
so nothing external depended on them, and this turned focus restoration from a
hard problem into a one-line lookup: every control carries `data-fk` =
`<node path>:<slot>`, `captureFocus()` reads it plus the caret offsets before the
rebuild and `restoreFocus()` puts them back. It also survives an undo.

**History entries are recorded after the render, not before.** This was a real
bug found in testing: `render()` can settle the document itself — an empty enum
value takes its first choice as it draws — so a pre-render snapshot described a
state that had never been on screen, and the first undo appeared to do nothing.
The constructor seeds the baseline after its first `sync()` for the same reason.

**Coalescing shape.** `noteEdit(key)` on each keystroke; a different key flushes
the previous burst; an idle timer (`historyIdle`, 500 ms), a blur, or any call
to `mutate()` also flushes. Chips are discrete and push immediately.

**Move buttons lead, drag follows.** Both call `moveChild(group, from, to)`.
Alt+↑/↓ is bound on the row so it needs no pointer. The buttons are disabled
rather than removed at the ends, so a row does not reflow as it travels.

**Drop hit-testing.** `siblingBounds(parent)` returns n+1 client-Y boundaries;
the nearest wins; `moveToBoundary` converts a boundary to an index. Flow uses
the `flowSpans` line ranges recorded during `renderFlow`; tree uses the
`[data-kce-child]` elements under the matching `.kce-group-children`.
`siblingIndent(parent)` insets the indicator to the level being reordered.

## Still true, still not done

- **Order remains presentational.** `evalGroup` has no short-circuiting, so
  neither the result nor which callbacks run depends on sibling order. If
  short-circuit evaluation is ever added, order becomes observable and this
  needs documenting as a semantic change.
- **Cross-group dragging** was deliberately left out. It overlaps heavily with
  what `+AND` / `+OR` and `AND(…)` / `OR(…)` already do, and it is what makes a
  drop ambiguous in a nested tree.
- No auto-scroll during a drag on a long rule.
