# 0.0.14 — operator alignment and the demo skin picker

Written 2026-09-03. A supplement to `design-record.md`, which carries the
running summary; this is the detail for the two changes in 0.0.14.

## The ragged operators

Ben sent a screenshot: in a group of three `State is equal to …` rows with values
"Alabama", "California", "Florida", the three `OR`s printed at three different x
positions. In the flow layout a connector is appended immediately after the row
it follows, so its position is whatever that row's width happens to be.

### Why it needed fixing rather than explaining away

The prose layout's entire argument, going back to the 0.0.2 design pass, is that
a rule should read like an equation on a blackboard. A ragged operator column is
exactly the thing that stops it reading that way.

### Two attempts

**Per group** was the first cut and fixed the reported case — the three State
`OR`s snapped to one column. But it left the Name group's `OR` at x=453 and the
State group's at x=407: two sibling groups, rows at the same indent, operators
46px apart. That read *worse* than the original raggedness, because the eye
compares the two columns directly.

**Per indent level** is what shipped. Rows at the same indent already read as a
column, so their operators join it; a deeper group is a different thought and
keeps its own. In the reported rule all three depth-2 operators now sit at one x.

`alignConnectors: 'group'` keeps the per-group behaviour. `false` disables it —
the escape hatch for the one bad case, where a single very long row drags its
neighbours' operators out to the right.

### Implementation

- `renderConnector` tags each connector with `data-conn-group`; `renderFlow`
  additionally tags it with `data-conn-depth`, which it knows for free.
- `alignConnectors()` buckets by depth (or group), clears **every** margin
  before measuring **any** — otherwise each pass measures against the last
  pass's padding and the column creeps rightward — takes the max `offsetLeft`
  per bucket, and pads the rest to it with `margin-left`.
- Called from `sync()` (not just `render()`), because typing widens an
  autosizing input without rebuilding anything, and from a rAF-throttled
  `resize` listener, because rows wrap at narrower widths.
- Tree layout is untouched: it already puts connectors on their own rows.

### The bug this surfaced

The column lagged one character behind while typing. `renderLiteralInput`
registered its `input` listener *before* calling `autosize()`, so on each
keystroke the sync (and therefore the measurement) ran before the field resized.
Autosize is now attached first. Harmless before 0.0.14; nothing else measured.

**Note for anything added later that measures a row:** listener order in
`renderLiteralInput` is load-bearing. Autosize must run first.

## The skin picker

Ben asked whether the demo could switch skins. It could not — `skins.html` shows
all five side by side, but on a fixed sample rule, so it cannot show you *your*
rule in each treatment, which is the thing you actually want to see.

- **index.html**: a compact `Skin` select above the main demo, calling
  `editor.setSkin()`. No rebuild, so the rule you built stays put.
- **demo.html**: `Skin` and `Theme` (system / light / dark) in the controls row.
  Both applied live via `setSkin()` / `setTheme()`, and both fed back into
  `attach()` so the choice survives a **Rebuild editor**, which does recreate the
  instance.
- `.skin-picker` / `.skin-hint` styles added to `assets/site.css`.

`tests/browser/bracket-weight.js` covers the picker: all five skins on both
pages, the flow↔tree layout switch (`lines` vs `groups` in the DOM), the rule
surviving all five, all three theme values, and the skin surviving a rebuild.
