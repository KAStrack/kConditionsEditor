# 0.0.16 — the add-button preview (and the left-aligned footer)

Written 2026-09-03. Supplements `design-record.md`.

## Footer

The problems list had `flex: 1 1 auto` and was eating the free space, pushing
Undo / Redo / Clear / Done to the right edge. It now takes a full row above them
(`flex: 1 1 100%`) and collapses with `:empty` — `sync()` sets `innerHTML = ''`
when there is nothing to report, so `:empty` is a valid test. Controls sit left.

## The preview

Ben asked for something like the `×` preview, for `+AND` / `+OR` / `AND(…)`.
He picked "ghost row + tinted group" from three options.

### The design

Two marks, one story:

- **Tint** = the rows that end up bracketed together, in the hue of the bracket
  being formed.
- **Ghost** = a dashed "new condition" placeholder where the new row lands, in
  the hue of the operator on the button.

Their relative position tells you whether the new condition lands inside or
outside the bracket, which is the whole difference between `+OR` and `OR(…)`:

| Button | Tint | Ghost |
|---|---|---|
| `+AND` (matching op) | the whole group, AND-blue | below, AND-blue |
| `+OR` on a row (opposite op) | only that row, OR-orange | below it, OR-orange |
| `+OR` beside an existing OR group | that group's rows, OR-orange | below, OR-orange |
| `OR(…)` | the whole group, **AND**-blue (it stays an AND group) | below and outside, **OR**-orange |

The two-hue split on `OR(…)` is what finally makes that button legible. Hence
`plan.op` (tint) and `plan.ghostOp` (ghost) are separate fields.

### Why it is trustworthy: plan functions

`addBeside` had a four-way decision inline. It is now `planAdd(group, index, op)`,
a pure function returning `{kind, op, ghostOp, group, at, node, enclosed}`;
`addBeside` executes the plan and `previewPlan` draws it. Same for
`planWrap` / `wrapAndContinue`. **The preview reads the same branch the click
takes**, so a change to the rules updates both at once. Without this the preview
would be a second implementation of the semantics, and would drift.

### The flicker rule

The ghost is **always inserted after the line the button sits on**, never before
it. I hit the failure first: if the ghost lands above the button, the button
moves out from under the pointer → `mouseleave` → ghost removed → button moves
back → `mouseenter` → loop. Anchoring to the button's own line makes that
impossible by construction, and it is the correct position in every case except
`extend`, where it is one line low.

`.kce-ghost` and `.kce-ghost-line` are `pointer-events: none` for the same
reason.

### Details

- `removalTargets` is now `subtreeTargets` (both previews use it).
- `clearPreview()` drops the removal tint, the grouping tint and the ghost
  together, so the two previews can never both be on screen.
- `.kce-will-group` background uses `!important`, per the 0.0.13 lesson.
- Bound on `mouseenter`/`mouseleave` **and** `focus`/`blur`, plus `click` to
  clear — though after a click the pointer is still on the (rebuilt) button, so
  the preview correctly re-arms for the *next* add.

## Fixed on the way

`blackboard` never defined `--kce-accent-soft`, so it inherited the light value:
hovering `+AND` painted a pale blue block on the dark board, and the new tint
would have done the same. It now sets its own. This is the four-places palette
convention biting a *pre-existing* gap that nothing had noticed.

## Testing note

`tests/browser/add-preview.js` had to learn how to point at an add button. They
are `max-width: 0` at rest, and in the **tree** layout the `.kce-connector`
holding them is itself zero-wide until revealed — so the thing to hover is the
row *above* the connector, not the connector. In **flow** it is the button's own
line. Hovering the button directly just lands on whatever is underneath, which
is what the first run did (and Playwright's "intercepts pointer events" error is
the signature of it).

The check asserts, per branch and per layout: which rows are tinted, the tint
hue, the ghost hue, that leaving clears everything, and that the button does not
move while previewing (the flicker check).

**Sequel, 0.0.21.** The focus trigger has a consequence for any *other* check:
a focused add button leaves its ghost in the DOM, and the ghost is inserted into
the flow layout's line list. A test that measures line positions after focusing
an add button measures the wrong line. See `hover-focus-reveal.js`.
