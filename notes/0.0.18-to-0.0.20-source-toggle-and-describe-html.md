# Notes — 0.0.18 to 0.0.20

Three small releases, one documentation-only. Written up together because 0.0.19
and 0.0.20 both came from the same kind of request: *"I want this, unless it
already exists — in which case tell me how."*

---

## 0.0.18 — SQL column names, documentation only

**Ben asked:** for SQL output, if a field's `column` is omitted, can it fall back
to `name` — or does it already?

It already did, and had since 0.0.4, in both SDKs. `columnFor(field)` returns
`field.column || field.name`. Nothing was wrong with the code; the docs simply
never said so, and the SQL examples all set `column` explicitly, which made it
look required.

Fixed by saying it out loud in README.md, docs.html and SPEC.md, and by removing
`column` from one example so the fallback is visible in the code rather than only
in prose.

**The lesson is about documentation, not SQL.** An example that always passes an
optional argument teaches readers that the argument is mandatory. If a default
matters, at least one example has to rely on it.

## 0.0.19 — showing the field again, and hiding something else

### `hideTextarea: 'toggle'`

A third value beside `true` and `false`. The field stays hidden, but a **Show
source** button in the footer puts it back. `setSourceVisible(true|false)` and
`isSourceVisible()` do the same from code; a `source` event fires either way.

Deliberately distinct from the *View source* button that `debug: true` adds:
that one shows the **document being generated**, this one shows the **field it is
written into**. Their labels are separate keys (`revealField` / `concealField`
versus `viewSource` / `hideSource`) so either can be renamed if both are on.

### `hideTarget`

A CSS selector, an element, or a list of either — hidden *instead of* the
textarea. Ben's case is the row that carries the field's label:

```js
hideTarget: document.querySelector('#conditions').closest('.row')
```

Without this, hiding the textarea leaves its `<label>` behind, labelling nothing.

Three things it has to get right:

- **The editor is inserted after the outermost hidden element**, not after the
  textarea. Inserting after the textarea puts the editor *inside* the row that is
  about to be hidden, and it is never seen. This is a line in CLAUDE.md, because
  anything that changes where the root is placed can break it silently.
- **The textarea is hidden regardless.** If the target does not contain it —
  naming only the label, say — the field joins the list. A raw JSON textarea
  beside the builder is never the intent.
- **A selector matching nothing warns and falls back** to hiding the textarea,
  rather than leaving the field on show.

`destroy()` restores everything it hid, targets included.

Also introduced `.kce-concealed`, a general form of the visually-hidden treatment
that was previously `textarea.kce-hidden-textarea` and so could only ever apply
to the field.

### A two-year-old bug found on the way

`debug: true` with `collapsible: false` threw, and the editor never rendered.
`footer.insertBefore(sourceButton, this.doneButton)` — but `doneButton` is only
appended when the editor is collapsible. Present since 0.0.4.

Nothing caught it because every test used one option or the other, never both.
**Cross the option combinations, not just the defaults.**

## 0.0.20 — `describeHtml()`

**Ben asked:** when viewing a set of conditions, could there be an option to show
the fields as HTML — `[fieldname]` becoming `<strong>fieldname</strong>`, and the
value maybe underlined?

Yes, and it turned out to be the natural shape for something `describe()` was
already doing badly: encoding structure in punctuation. The brackets around a
field and the quotes around a value exist because plain text has nothing else.
Given markup, they become a bold field and an underlined value, and the sentence
reads as a sentence.

Ben chose **dashed underline plus the value colour** for values (matching the
editor's own free-text inputs), and **both scopes** — standalone SDK function and
the editor's collapsed summary.

### Three decisions

**One walker, two formatters.** `describe()` was refactored into
`describeWith(document, options, format)`; text and HTML are that same function
with different leaf formatting.

Two separate renderings would have drifted. One of them would eventually have
bracketed a nested group differently or put `NOT` somewhere else, and nothing
would have caught it — the two are never compared at runtime. This is the same
principle as the `planAdd` / `planWrap` plan functions from 0.0.16: when two
things must agree, make them one thing.

**Escaping is not optional.** No flag turns it off. A document arrives from a
browser, and so do the field labels and `emptyText` rendered alongside it, so
`<img src=x onerror=…>` in a value comes back as text. This is also why it is a
*separate function* rather than an option on `describe()`: a boolean parameter
somewhere in an options object is easy to read past, whereas `describeHtml()` at
the call site says out loud that markup is being produced.

**The `.kcd-*` styles are not scoped to the editor.** A rule is most often shown
on a page that has no editor on it — a confirmation screen, an audit log, an
email. The block defers to the editor's `--kce-*` tokens when they are present
and falls back to its own otherwise, so it matches the theme when the editor is
there and still looks right when it is not. `docs.html` demonstrates this by
loading only `src/k-conditions-editor.css` and rendering a sample; verified with
a with/without stylesheet comparison over a thousand elements, zero style drift
onto the page's own chrome.

### Classes

`.kcd` wraps the whole rendering; inside it `.kcd-field` (a `<strong>`),
`.kcd-op`, `.kcd-value`, `.kcd-list` / `.kcd-sep`, `.kcd-logic` (plus `.kcd-and`
/ `.kcd-or`), `.kcd-not`, `.kcd-paren`, and `.kcd-join` for the word between the
halves of a two-value operator. No inline styles, so restyling is a matter of
overriding classes.

### `summaryHtml`

Default `false`. When true the editor's collapsed summary is rendered with
`describeHtml()`. `editor.describe()` and `editor.describeHtml()` are both
available directly and use the editor's own fields and operators.

### The bug the fixtures found

**PHP `describe()` ignored choice labels.** It rendered
`[State] is equal to "FL"` where JavaScript rendered
`[State] is equal to "Florida"`. `Support\Values` had no `normaliseChoices()` at
all, so the three accepted `choices` shapes were never resolved on that side.

Present since choices were introduced in 0.0.4, and invisible because
`describe()` had **no shared fixtures**. The conformance suite covered evaluation
and SQL, where a display label is irrelevant — the stored value is what gets
compared and what goes in the query. `describe()` is the only place the label
matters, and it was the only place not being compared across languages.

Fixed by adding `Values::normaliseChoices()` and pinning it with 18 new
`describeCases` fixtures, each asserting **both** the text and the HTML
byte-for-byte in both languages, plus a check that no unescaped tag survives.
JS 83 → 102 assertions, PHP 78 → 96.

**The lesson:** a conformance suite only pins what it compares. Any output an SDK
produces that no fixture asserts is free to differ between languages, and will.
