# Notes — 0.0.26

The editor was designed on a wide page and judged on one. KAStrack put it in a
545px dialog, and it fell apart in a way none of the tests could see, because
none of them ran it there.

## The report

> the buttons show up on hover, but they seem small, highlights occur
> everywhere, and it just seems squirrelly.

It came with measurements taken off the live widget (prose skin, a condition
row 545px wide, `--kce-font-size` resolving to 12.19px), and they split the
feeling into separate faults. The report's own suggestion for the first one was
right in mechanism and wrong about where the width came from, which is worth
recording.

---

## 1. A row wrapped instead of shrinking

`.kce-condition` was `display: flex; flex-wrap: wrap`. Its children measured
575px inside a 545px row. In a wrapping flex container, line-breaking is decided
*before* any item is allowed to shrink, so the 30px of overflow did not narrow
the value input: it put `.kce-move` and `.kce-remove` on a second flex line.

The consequences, measured:

- every row was 56.2px tall instead of 31.2px, reserving a line for controls
  that are invisible until hover;
- on hover the controls appeared 34px *below* the thing being pointed at;
- the hover tint spanned the full 545px of both flex lines, while what it
  revealed was three glyphs in a corner.

The threshold was sharp: 612px fine, 564px broken. A wide host never saw it.

**Fix.** Rows never wrap. The value slot is the thing that gives up width — it
has `flex-shrink: 100`, so it takes nearly all of a shortfall, and it still
wraps *inside itself*, which is how `between` and the tag list fold. The field
and operator names may shrink (and ellipsis) only once the value slot is down to
its 60px minimum. The grip, arrows, NOT and × never shrink. Boxed had the same
fault with no host CSS at all: at 545px its nested × wrapped.

## 2. The width was the host's

Reproducing at 545px with clean CSS, the row *fit*: the prose value slot
autosizes to about 124px and the row is 377px wide. In the screenshots the input
was a 384px bordered, rounded, 42px-tall box — 24rem exactly. That is the
dialog's form stylesheet reaching into the editor. It was also why the `OR`
after each row sat on a line of its own: the condition had grown to the full
line width, so the connector wrapped.

**Fix.** `.kce .kce-tree input.kce-input` pins `width: auto` (so `autosize()`'s
`size` attribute governs again), height, min/max, margin, radius, shadow and
line-height. The `<select>` overlays are pinned to their labels the same way.
Buttons get `margin`, `min-width`, `min-height`, `box-shadow` and
`text-transform` reset under `:where(button)`, so the editor's own button rules
can still set a margin. The specificity beats element and class-scoped host
rules. An ID-scoped host rule still wins; README says how to exclude the editor
there.

Offered `!important` instead, Ben chose the specificity reset: a host that
restyles the editor on purpose should not have to escalate to do it.

## 3. Small targets, faint glyphs

WCAG 2.2's minimum target is 24×24. The grip was 12×10 — a 120px² target for a
drag handle. The arrows and the prose × were 20×20, the `+AND` / `+OR` buttons
16px tall, the AND / OR word 15px. And the reveal was `opacity: 0.55` on a
`#6a7482` glyph — about 2:1 against white, under the 3:1 a control needs. The
"resting 0.25" arrow was the disabled one at the end of a list.

**Fix.**

- Grip, arrows and × are 24×24 boxes with negative margins that hand back the
  extra, so the row is no taller. The grip's box starts at the row's content
  edge (not before it), because at depth 0 anything further left is clipped by
  the tree's `overflow-x: auto`.
- `.kce-add` and `.kce-connector-btn` keep their small labels and get a
  transparent `::before` that extends the hit area to 24px around the centre —
  `top: min(0px, calc(50% - 12px))` and its siblings, so a label already larger
  than 24px is not shrunk. Their font sizes are floored at 10px; 0.7em of a
  12px host is 8.5px.
- Reveal is a switch: opacity 0 → 1, with `--kce-text-muted` (4.7:1) carrying
  the quiet. Same for boxed's permanent 0.5, and for the tree skins' outer group
  rails, which showed at 0.4 when a nested group was hovered.
- The end-of-list arrow is `visibility: hidden` — Ben's pick over "readable but
  muted". It keeps its space, which was the point of disabling rather than
  removing it.
- The reveal selectors were nine overlapping rules; they are one per row
  container now (`.kce-line` in flow, `.kce-condition` / `.kce-group-head` in
  tree), each with its `:focus-within` twin. The prose × was on a different
  trigger from the grip and arrows (the condition, not the line), so pointing at
  the AND after a row showed two of its three controls. It is on the line now.
- `@media (hover: none)`: on a touch screen everything a row reveals is shown at
  rest, add buttons included. Ben chose this over making prose always show its
  controls, which would have put them into the equation the skin argues for.

## Found by measuring the same width

The new browser check ran the editor at 640 / 564 / 545 / 420 with a hostile
host stylesheet and found three more:

- **Hidden dialogs never aligned.** `alignConnectors()` re-measured only on
  `window` resize. An editor attached inside a `display: none` dialog measured
  every offset as zero, and opening the dialog changed nothing. A
  `ResizeObserver` on the tree now re-runs the layout pass when the tree's
  *width* changes (height changes with every edit and is ignored).
- **Alignment could wrap a line.** Pushing a connector out to the column could
  send it — or, on the row before a group, the bracket and the group's tools
  after it — onto a second line. Each push is now checked against the line's
  height and undone if it grew it. A ragged operator is cosmetic; a wrapped
  line is not.
- **A prose group's tools wrapped under its bracket.** They ride on the opening
  line, after `(`, at opacity 0 — and about 136px wide. At 545px they wrapped,
  reserving exactly the blank band the rows had just stopped reserving.
  `fitGroupTools()` measures whether they fit after the bracket (from the
  bracket's right edge and their own width, without moving anything) and, when
  they do not, moves them to the group's closing line — otherwise a lone `)` —
  unless that line also opens the next group, where they would be ambiguous. An
  element is moved only when its place changes, and focus is restored if it was
  inside, because this runs on every `sync()`.

The tree skins have the equivalent: their group rail is parked to the right of
the expression, and only a 700px *viewport* query folded it in. `fitGroupRail()`
measures whether any rail overflows the tree and sets `kce-rail-inside`, which
applies the narrow-screen treatment.

## The general case

**A narrow host is not a narrow screen.** Everything that depended on the
editor's width either had no answer for a dialog or answered from the viewport.
The checks now run at dialog widths, with a host stylesheet that tries to
restyle the editor's inputs and buttons, and judge by what is painted: control
centres against the field's line after a real hover, `elementFromPoint` 11px
out from each control's centre, and contrast composited from computed colours
and every ancestor's opacity. The script fails 108 of its 229 checks against
0.0.25.

## Not done

- The tree skins draw an empty tail-connector row inside every group, which
  reads as a band under the group's last row. Same shape of problem; separate
  change.
- Container queries would express "narrow host" in CSS, but
  `container-type: inline-size` zeroes the intrinsic width of whatever it is
  on, and an editor inside a shrink-to-fit host would collapse. Measuring in JS
  avoids that.
