# Notes — 0.1.2

A request from the Herräng Dance Camp system (HDC), for a new admin page
(Camp Staff → Applications Review) where staff filter 300–400 applicants by a
rule evaluated in the browser over rows the page already holds. HDC's rules
stopped it from using 0.1.1 as it was:

- every string a person sees or hears goes through translation (English,
  Swedish, Chinese);
- every `<select>` is a kselect widget (Ben's own library, 1.9.0);
- every page passes axe (WCAG 2.1 AA) in light and dark;
- vendored libraries come from a tagged release.

HDC had already written its wrapper (`modules/conditions-editor.js`) against
the API it hoped for, which was useful: it showed how a real host would call
the hooks, including the one way it would call them wrong (below).

## Labels: one object, three maps, templates

`labels` was already the one place for UI strings. What was missing was
everything that bypassed it, so the work was finding all of it — and then
making sure it stays found. Two decisions:

- **Maps merge a level down.** `operators`, `groups` and `problems` are maps
  inside `labels`, merged key by key, so translating `eq` does not erase every
  other operator's name. Top-level keys still replace.
- **Templates, not concatenation.** `'Remove ' + v` fixes the word order for
  every language. A label holding `{value}` / `{operator}` is filled where it
  is used (`fillTemplate`, one helper in the evaluator, used by both the
  editor and `validateDocument()`; mirrored in PHP as `Support\Labels`).

The check that keeps it found (`tests/browser/labels-everywhere.js`) replaces
every label with a marker naming its key, drives the editor through every
state a person meets, and reads every text node and every aria-label, title,
placeholder, option and optgroup. Anything left after the markers, the rule's
own data and punctuation is a string that bypassed `labels`. It was checked
by putting one English aria-label back and watching it fail.

The debug panel's body (SQL, JSON, `path: message`) is left in English on
purpose: it is developer output, not interface.

## describe() takes the same labels

The summary is the other half of a translated rule. `describe()` already took
`fields` and `operators` (custom operator *definitions*), so the new option is
`labels` — the editor's own object, passed as is — rather than a second pair
of maps. One object for both is the "make them one thing" rule again: a host
cannot translate the editor and forget the summary. The HTML formatter now
classes `kcd-or` by the operator, not by the word — it compared the word with
"OR", which a translation would have broken.

## The {value} slot

"is within the last N days" read "is within the last N days [7]" on the row
and "is within the last N days 7" in the summary — in English. HDC asked only
to be told where the operand goes so it could word translations around it; a
slot in the label does better, for every language, so it is a slot.

- **Where it is split.** `splitOperatorLabel()` returns head, the whitespace
  either side, and tail. The whitespace is kept as written: Chinese wants none
  round a number (`在过去7天内`), English wants a space.
- **On the row**, the select's shell label shows the head (an option carries
  `data-kce-head`), the value follows, then a `.kce-op-tail` span drawn as the
  operator is. The option text, in the list, is the whole label with `…` in
  the slot: the list is where a reader compares operators, and "is within the
  last" alone is ambiguous.
- **In English too** (Ben's choice, offered as a trade-off because it changes
  `describe()` output for four operators in both SDKs).
- **With a decorated operator select** the slot is given up: the widget shows
  the option's whole text, so a tail after the value would say "days" twice.
  The documented way to keep it is to decline `'operator'`.

## decorateSelect

The constraint that shaped it: render() rebuilds the tree, so every select is
new on every render, and a widget built on the old one is garbage — with a
portalled dropdown, garbage outside the editor. So the hook is called on every
render, after the tree is complete and in the page (the widget may measure),
before the layout pass (so the layout measures the widget). And it has a
partner, `releaseSelect`, called before a render discards the select and on
`destroy()`. Without it, kselect leaves one dropdown in `<body>` per select per
render; with HDC's 40 fields and a busy rule that is hundreds within minutes.

Things decided:

- **The editor never learns what the widget is.** It goes on listening to the
  select's `change`, which kselect (and most widgets of its kind) dispatches.
- **`false` declines.** The decision is the host's per role — HDC may want the
  operator left native to keep the slot.
- **A list of choices becomes `<select multiple>`** when a host decorates. The
  chips plus a "+ add…" select was the editor's answer to a native multi
  select being unusable; a widget with tags and checkboxes is better than
  both, and decorating the "+ add…" select would have broken anyway (the chip
  redraw empties its box, widget and all). Declining `'values'` keeps chips.
- **Focus.** `captureFocus()` keyed on `data-fk` of the active element, which
  is the widget's button. It now resolves through the select's shell
  (`.kce-sel`) or a `data-kce-for`, and, when focus is in a widget's portalled
  list at the moment of the change, falls back to the select that is changing
  (held by `onSelect()` while its handler runs). Restoring calls
  `focusSelect`, else focuses the first focusable thing in the shell — which
  is kselect's combobox, so HDC needs no hook at all.
- **Asynchronous widgets.** HDC's `enhanceSelect` awaits an `import()`. A
  returned promise is waited for. HDC's own wrapper did not return it (`{
  enhanceSelect(select); }`), which is the likely mistake, so focus is also
  retried for a few frames while it is lost — on the hidden select or the
  body — and stops the moment it is anywhere else.
- **Layout.** A decorated shell has no label span and no chevron, and does not
  shrink (a widget cannot ellipsis); `fitRows()` skips it and a row too wide
  scrolls. `alignConnectorsBelow()` aligns the AND / OR to the field shell
  when there is no label. Each decorated shell is watched (a
  `ResizeObserver`), so a widget that lands late — promise or not — or that
  changes width as it is used (a multi-select's tags) re-runs the layout. The
  first check for this passed with the observer removed, because the AND /
  OR below a row aligns to the shell's left edge, which does not move; the
  inline operator column does, and that is what the check now measures.

Checked against kselect 1.9.0 itself, inside HDC's `app.css` and its two theme
files, in light and dark. The committed check uses a stand-in widget built the
same way (hidden select, sibling combobox, portalled list, async), because a
test cannot depend on another repository.

## Accessibility

axe found more than the request listed. In the editor's own default colours,
light theme: the muted grey (operators, hints) was 4.23:1 on a hovered row,
ledger's operator grey 3.85:1 at rest, the +AND hover 4.25:1. Dark: the
Clear confirmation 3.0:1, boxed's active OR 2.2:1. Blackboard inherited the
light theme's `--kce-accent-strong` (1.3:1) — the CLAUDE.md trap exactly. And
three scrolling `<pre>`s were unreachable by keyboard.

- The muted grey moves to `#5f6875` (≥ 4.9:1 on every light surface it sits
  on). Visibly a shade darker; the hierarchy holds.
- The add-button hover colour is a `color-mix` 80% of the AND / OR hue towards
  `--kce-text`. That keeps the hue and clears AA in both themes — and for a
  host's own `--kce-and`, since it moves towards whatever the text colour is.
- `--kce-danger-text` is new, in all four places (light, both dark blocks,
  blackboard).

The check (`tests/browser/accessibility.js`) runs every skin × three themes ×
two control modes × nine states, so a hover-only control is judged where it
is painted. 270 audits, about 80 seconds.

## dist/ committed

HDC vendors from a tag; a tag had no built files. Committing `dist/` (Ben's
choice over GitHub release assets) means every tag is vendorable, and jsDelivr
serves it by tag. The risk of a committed build is a stale one, so
`tests/js/dist.test.js` builds in memory and compares byte for byte, on
`npm test`; `build.js` exports `render()` for it. `LICENSE` is copied into
`dist/`, so the folder stands alone.
