# Notes — 0.1.5

HDC (the Herräng Dance Camp system) went live on 0.1.4 with the built-in
kSelect (its own vendored 1.11.1, passed as `kselect: Kselect`), the prose
skin, `controls: 'always'`, the host's text at 16px (`--kce-font-size:
1rem`), and about 80 fields. Many field names are whole questions, and a
rating grid's items are `"{question}: {item}"`, so the end of a name is what
tells two fields apart. Two problems came up the same day.

## A layout that fed itself

**Seen:** after a pick, or on reload, the field's kSelect narrowed (or
widened) a pixel a frame and never stopped: 600px to 57px in nine seconds,
the operator beside it growing by the same.

**Two causes, either enough to stop it:**

- `fitRows()` gives a name a floor (about 2.5em, or its own width if
  shorter) as a `min-width` on its shell, plus an allowance for the chevron:
  the shell's width minus the label's. It cleared the row's minimum before
  measuring, but not the shell's. Once the shell's own min-width was what
  sized it, the "chevron" was last pass's minimum minus the label, and the
  new minimum was last pass's plus whatever `Math.ceil` and a fractional
  label width added. A pass that reads its own result is a ratchet.
- The shells of decorated selects are watched (a `ResizeObserver`, 0.1.2) so
  a widget that lands late re-runs the layout. It could not tell a widget
  changing size from the layout changing the widget's shell — so the ratchet
  had an engine, a pass per frame.

It began only where a name was under the floor, so `min(natural, floor)` was
the label's own width and the label did not stretch with the shell: "is yes"
at 16px, "is" at any size. Every check ran at the default 15px with longer
operators, and the kSelect checks used one-word field names.

**Fixes.**

- `fitRows()` is now clear → read → write over all the names at once. The
  read holds each name shell at its natural width (`flex: none` for the
  read): with the minimum cleared, a squeezed shell can be narrower than its
  own chevron, and the allowance came out short — "is" was drawn "i.". As a
  side effect the page lays out once per pass instead of once per shell.
- `fitLayout()` ends by noting each watched shell's size
  (`noteShellSizes()`); the watch re-runs the layout only for an entry whose
  size differs from that. So no measured layout can drive itself through
  the watch, whatever it does — the check proves this with a pass rigged to
  change a shell every time, which runs once and stops.

The general lesson is the one CLAUDE.md now carries: anything a layout pass
writes, a later pass must not read as input, and anything that re-runs the
layout on a size change must be able to tell the layout's own writes apart.

## Long names

**Closed.** A name gives up width as the row does and ends in "…". It now
has a tooltip with the whole name, while — and only while — it is cut
(`markClippedNames()`, at the end of each layout pass; a tooltip repeating
what is in full view is noise). On the select's *shell*, not the control:
the whole name is already the control's value to a screen reader (the "…"
is painted, not in the text), and a `title` on the control would be read a
second time as its description. "Cut" is measured with a `Range`, which has
the text's fractional width; `scrollWidth` / `clientWidth` round, and called
"is" cut by a pixel it was not.

**Open.** kSelect sets its list's width to its control's — here, a word —
and the editor's layer clamped it to 14em–28em, so every question ended at
the same place. Now:

- option text and group names wrap in the editor's layer;
- the list is as wide as its longest option, up to `min(36em, 100vw −
  16px)`. Measured once as it opens (`fitKselectList()`, on `kselect:open`)
  and kept as a `min-width`, so filtering does not change the width under
  the pointer. It runs after kSelect has scrolled to the current choice
  (which kSelect centres), so it keeps that scroll, and moves a list that
  opened upwards so its foot stays on the control;
- the list is kept on screen. kSelect keeps it in the viewport by the
  control's width, not the list's, so a wide list opened near the right ran
  off. kSelect re-places the list as the page scrolls, so the editor watches
  the list's `style` (a `MutationObserver`) and moves it back each time; its
  own write does not move it again, so the watch settles.

**Where wrapping belongs.** In kSelect as well as here. Any host with long
options meets it, and kSelect is the one placing the list, so two changes
there would serve everyone: an option to wrap option text (or a documented
`--ks-option-white-space` token), and keeping the list on screen by its own
width rather than its control's. The editor does both for its own layer
regardless, because HDC vendors 1.11.1 and the editor has to be right with
the kSelect it is given; when kSelect does them, the editor's versions
become no-ops (the measured width is the same, and nothing is off screen to
move).

## The kSelect font size

`--ks-font-size` was `0.9375rem` on the closed control and the layer, which
was the editor's default size written out rather than referred to. It is
`1em` now: the row the control sits in, and the layer, which is a `.kce`
and so has `font-size: var(--kce-font-size)`.

## The suite

`tests/browser/kselect-long-names.js` is new: HDC's shape (16px text, a short
operator, whole-question field names, `controls: 'always'`). Run against
0.1.4 it reproduces the report — 61 layout passes in a second at rest, the
operator going from 49px to 110px — and each part of the fix was checked by
taking it out again and watching its assertion fail.

`one-line-rows.js` had grown to 246 s of the runner's 300 s per script when
0.1.3 added its kSelect passes, which is how `no-overlaps.js` came to time
out in 0.1.3. Its kSelect half now runs as `one-line-rows-kselect.js`, the
same split `no-overlaps-kselect.js` made.
