# Notes — 0.1.6

KAStrack has multi-value fields — a users field, "Assigned To" — that its SQL
exposes as two columns: `--ID_FOR_Assigned To`, a JSON array of string IDs
(`["3184"]`, `["3184","3152"]`, `[]`), and `Assigned To`, display names in no
consistent format (a plain name, a JSON array of names, `[]`). Its PHP helper
declared these fields `type: 'text'` on the display column, so `is not empty`
was `(col IS NOT NULL AND col <> '')`, which `[]` passes: a rule "colour
unassigned cards, except where Assigned To is not empty" excepted every card.
`JSON_CONTAINS` on the display column failed the whole query, because a plain
name is not JSON.

`type: 'list'` was the right type and did not help on its own: the SQL builder
ignores the type for existence operators, and `includes_any` / `includes_all`
emitted no SQL at all ("a multi-valued column has no portable storage shape").
The field option says which shape it is.

## One option, read in one place

`storage: 'json'` on the field definition — next to `column`, because it
describes the column. A string rather than an object: nothing about the format
is configurable that should be (the empty spellings are a fact about save
paths, not a preference; the elements are strings because `JSON_CONTAINS` is
type-strict), and a string leaves room for `'csv'` later. Unknown values are
ignored, so a typo behaves as no option rather than throwing in a page.

It is host configuration, not document content. Nothing is copied into the
document, so the schema is unchanged: a rule saved before the option existed
gains it the moment the host declares it, with no re-save, and the same rule
can run against a schema that stores the field differently. The SQL builder
already took the host's `fields` (for `column`); the evaluators gained a
`fields` option to hear `storage`, and read nothing else from it.

Each SDK reads it through one helper — JS `KConditions.helpers.fieldStorage()`
and `readJsonList()`, PHP `Support\JsonStorage::storage()` and `read()` — and
the SQL builders read the empty spellings and the operand filter from the same
place (`JSON_EMPTY_FORMS`, `jsonListOperands()` / `JsonStorage::operands()`),
so the evaluator and the SQL of one SDK cannot drift, and the shared fixtures
hold the two SDKs together.

## Agreement with the SQL decided the reading

The request gave a rule for empty (NULL, `''`, or JSON decoding to `null`, `""`,
`[]` or an array of empty elements, decoding twice when the first result is a
string) and a SQL shape tested on the live site (a list of empty spellings, and
`JSON_CONTAINS` guarded by `JSON_VALID` in a `CASE`). The two disagree at the
edges, and a rule that colours a board in SQL and previews in the browser must
pick the same rows in both. So a private MySQL 8.4 (a `TEXT` and a native
`JSON` column) and SQLite ran every operator, plain and negated, over thirty
stored forms, and each disagreement was settled:

- **A list saved twice** (`"[\"3184\"]"`). Decoding it twice for its contents
  finds 3184; no dialect can decode twice. The second decoding is kept for
  emptiness only — the rule's purpose — and its contents are not read.
- **Text that is not JSON** (`claude claudesson (claude)`). Treating it as a
  list of one is what a person might expect, but the SQL cannot (`JSON_VALID`
  is false, so the guard gives 0). It is something that names nothing: not
  empty, includes no value. In the real data it occurs only in the display
  column, which a JSON-stored field should not point at.
- **A number element** (`[3184]`) is not the string `"3184"`, as
  `JSON_CONTAINS` says. The evaluators compare elements as strings, but only
  string elements.
- **An operand that is itself empty** (`""`, `"[]"`) could match `["[]"]` in SQL
  and never in an evaluator, which skips empty elements. Such operands are
  dropped, in both, through the shared operand helper.
- **SQLite's `json_each`** walks an object's members, which `JSON_CONTAINS` does
  not; object keys (text, where array indexes are numbers) are filtered out.
- **`[null]` and `"[\"\"]"`** are empty by the rule, and cost one list entry each
  in the SQL, so they were added to the user's seven spellings.

Two remain, documented in SPEC §7: whitespace inside the brackets (`[ ]`) is
empty to the evaluators but not to the SQL, which compares spellings, and
MySQL's `JSON_CONTAINS` looks inside nested arrays. No save path is known to
write either. The check is `tests/db/json-storage.js` (`npm run test:db`; renamed
`tests/db/sql-vs-evaluator.js` in 0.1.7, when it took on `countAsBlank`):
SQLite always, MySQL when `KCE_MYSQL` names a server. It is not in `test:all`,
which needs no database, and it fails on any disagreement but those two.

## `is set` means `is not empty`

A list column clears to `[]` on one save path and to NULL on another, so "set
but empty" is nothing a person could ask about, and "is not set" must not miss
the `[]` rows — that miss is the very bug. The evaluators and the SQL treat the
pair as the empty pair, and the editor stops offering them (two names for one
question) unless a field's `operators` names them. A rule that already uses one
keeps it.

## Other operators on JSON text

`eq`, `contains`, `in_list` and the rest are not offered for a list. If a rule
holds one (saved when the field was `text`), the evaluators hand the operator
the decoded value, as for an array passed in directly, and the SQL builders
refuse it through `unsupportedPolicy`: `col = '3184'` against `["3184"]` is SQL
that looks right and never matches. A custom operator's `sql` template is used
as written; a `values` custom operator without one is refused the same way.

## A saved rule the fields no longer fit

Asked to check that a rule saved with a now-unavailable operator loads sensibly,
the editor turned out not to: the operator `<select>` was built from the field's
current list alone, so with the saved operator missing the browser selected the
first option. A saved `contains` on a now-list field painted "includes any of"
while the document still held `contains` and its text value. A field the host no
longer listed did the same — the first field painted over it. Nothing broke, but
the row misreported the rule, and the next pick in that select would have
replaced something the person never saw.

The compare-with list already had the rule: show what the document holds. The
row's own field and operator now follow it — the stray operator under its own
heading after the field's operators (an operator with no definition at all, by
its name, with no heading), the stray field by its name — and the stray goes once
something else is picked. `tests/browser/json-storage.js` judges both by the text
the shells paint, and fails on 0.1.5's editor.
