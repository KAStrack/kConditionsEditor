# Notes — 0.1.7

0.1.6 fixed `[]` passing *is not empty* for a field declared `storage: 'json'`.
KAStrack then chose to offer its multi-user fields as **text** for now — the
names column (`Assigned To`, a plain name, a JSON array of names, or `[]`), the
text operators — and `storage: 'json'` cannot do that: it makes the field a list
and refuses `contains` and `eq` on JSON text. So the field was back to `type:
'text'`, *is not empty* back to `col <> ''`, and the bug back with it.

## The option

`countAsBlank` names the stored values that count as empty besides NULL and
`''`. Two shapes, kept apart on purpose:

- **a string is a preset.** `'json'` is `JSON_EMPTY_FORMS`, the constant
  `storage: 'json'` lists — not a copy of it — so the two cannot drift.
- **an array is values**, every element literal. `['json']` is the text `json`.
  Mixing a preset name into an array was ruled out because `json` (or a future
  preset's name) can be a real stored value; a preset is only ever the whole
  option, which leaves room for more.

An unknown preset is ignored, as an unknown `storage` is: a typo behaves as no
option rather than throwing in a page. Array elements that are not strings are
ignored, and an array with nothing left is no option at all — `countAsBlank: []`
from a host building the list dynamically should not quietly change what *is
set* means.

## Only the existence operators

*Is empty* / *is not empty* use the set. Everything else — `contains`, `eq`,
`starts_with`, a callback, a custom operator — gets the stored value exactly as
without the option, and nothing is refused. That is the whole difference from
`storage: 'json'`, and the reason the option exists.

*Is set* / *is not set* follow 0.1.6: they mean *is not empty* / *is empty*.
The argument is the same one — the column clears to `[]` on one save path and
NULL on another, so "set but empty" is nothing a person asks about, and *is not
set* keeping the `[]` rows is the very bug. The editor stops offering the pair
beside *is empty* / *is not empty* (two names for one question) unless a field's
`operators` names them, and a rule that already uses one keeps it and shows it.

## Exact, and why the SQL changed shape

The request suggested `CAST(col AS CHAR) IN ('', …)` and exact, case-sensitive,
untrimmed matching in the evaluators. Those disagree on a real server. MySQL
8.4's default collation, `utf8mb4_0900_ai_ci`, is case- and accent-insensitive,
so with `countAsBlank: ['N/A']` the SQL called `n/a` blank and the evaluator did
not — and with `['é']`, `É`. `COLLATE utf8mb4_bin` is not the cure: it is PAD
SPACE, so `' '` equals `''` and `N/A ` equals `N/A` (MariaDB's defaults are all
PAD SPACE). A binary string has no pad attribute and no case, so the SQL text is
`CAST(CAST(col AS CHAR) AS BINARY)`: the inner cast reads a native JSON column
and brings a latin1 column into the connection's character set, which the
literals are in; the outer one compares bytes. SQLite needed `COLLATE BINARY`,
because a cast of a column keeps the column's collation (a `COLLATE NOCASE`
column compared without case).

Folding the evaluators instead was the other way to agree, and was rejected: a
collation is per column and per server, the evaluators cannot know it, and
"exact" is what the request asked for. For the same reason the evaluators'
`caseInsensitive` option does not touch the blank set.

The same probe found 0.1.6's JSON SQL had the bug too: `NULL`, `Null` and
`[NULL]` (invalid JSON — not empty to the evaluators) matched the spelling
`null`. It now uses the same exact text. `tests/db/sql-vs-evaluator.js` fails
on 0.1.6's plain cast with exactly those rows, plus `n/a` and `É`.

## The evaluators

A string is compared with the set as it is. That means `'json'` is a list of
spellings in the evaluators too — `[ ]` and `["",""]` are not blank on a text
field — because the SQL compares spellings and the two must pick the same rows.
(On a `storage: 'json'` field those are empty by the JSON rule; the SQL's gap
there is SPEC §7.1's documented one, and an array in `countAsBlank` is now a way
to close it for the spellings a host's data holds.)

A value that arrives already decoded has no spelling. It is compared by its
text (`asString()`: digits for a number, compact JSON for an array or object),
and under `'json'` an array of empty elements counts too, as the request asked
— "as with storage: 'json'". The SQL never sees a decoded value, so this cannot
disagree with it.

## With `storage: 'json'`

Meaningful, so allowed rather than rejected. `'json'` adds nothing. An array
adds stored values that are empty whatever they decode to, and — since empty
means holding nothing — that *includes any of* finds nothing in. The SQL adds
the values to the existence list and `AND <text> NOT IN (<values>)` to the
`JSON_VALID` guard, so a list counted blank never reaches `JSON_CONTAINS`.

## Dialects

MySQL / MariaDB and SQLite, the two that were run. PostgreSQL would very likely
work with a plain `CAST(col AS TEXT)` (its default collations are
deterministic), but PGlite could not be installed in the sandbox to prove it, so
it falls to `unsupportedPolicy` with SQL Server and `standard`, for the four
existence operators only.

Testing `mariadb` showed the JS builder had never resolved dialect aliases: it
kept `mariadb` as the dialect name, so every table keyed by `mysql` missed it —
`storage: 'json'` on MariaDB fell to the unsupported policy in JS (PHP always
resolved aliases), the result reported `mariadb` where PHP said `mysql`, and a
document's labels were matched by the alias. The JS builder now resolves them
as PHP does.

## The checks

69 evaluation, 24 SQL and 2 describe fixtures (47 of them fail on 0.1.6; the
rest pin what must not change). A JS/PHP grid of 6240 evaluations and 1920 SQL
builds outside the fixtures agreed throughout. `tests/db/sql-vs-evaluator.js`
runs both options on MySQL 8.4 (TEXT under the default collation, and a JSON
column, where the evaluator is given the server's own text back) and SQLite
(plain and NOCASE): 16,468 row checks, every disagreement one SPEC §7
documents. `tests/browser/count-as-blank.js` judges the editor by what it
paints, and fails five checks on 0.1.6.
